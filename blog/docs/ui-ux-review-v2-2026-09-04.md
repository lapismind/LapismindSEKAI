# 博客美术 UI / 用户体验评测 v2

> 评测日期：2026-09-04
> 范围：`blog.qmzhj.top` 首页、博客列表、文章页，以及对应 Astro / CSS / Vue 源码
> 方法：源码审阅 + Playwright 320 / 375 / 768 / 1440px 多视口实测 + 键盘焦点与资源传输检查
> 说明：当前模型不能读取截图内容，因此不声称做了主观“看图打分”。截图保留在 `.planning/2026-09-04-blog-ui-ux-review/` 供人工对照；下列结论来自可复核的布局、样式、交互和资源数据。

## 1. 总体结论

这个站不需要换风格，核心视觉方向是成立的：真冬紫、霞鹜文楷、卡面、Live2D、箱曲电台已经构成很明确的个人识别度。主要优化空间不在“再加更多效果”，而在按页面和设备控制效果密度。

当前最值得做的事有四件：

1. 修复 320px 小屏横向溢出。
2. 降低首页 Live2D 的首屏加载和移动端占位成本。
3. 把移动端文章目录移到正文前或改成顶部/侧边浮动入口。
4. 补齐统一的键盘焦点和 44px 触控目标。

一句话评价：**美术辨识度强，内容排版基础好；桌面端成熟，移动端与无障碍细节还没有完全跟上视觉完成度。**

## 2. 做得好的部分

### 2.1 品牌不是模板拼出来的

- `--hue-accent: 283` 经 OKLCH 推导亮暗主题，主色来源清楚，组件没有到处散落互相打架的紫色。
- 卡面 Hero、真冬主题色、Live2D、箱曲电台、日中双语文字共同表达同一个世界观，记忆点远高于通用个人博客模板。
- Header、卡片、Footer、评论区和文章正文使用同一套圆角、边框、阴影和色彩变量，8 月审阅里评论区的库存紫色问题已修复。

### 2.2 阅读排版基础扎实

- 桌面正文宽度约 `822px`，移动端 `335px`，没有横跨整屏的超长行。
- 正文约 `16.48px / 31.31px`，全局桌面基准 `18px / 1.85`，中文长文的行距比较舒展。
- `h2`、`h3`、引用、代码块、表格有明确层级；文章页有阅读进度、阅读时长、更新时间和目录。
- 375px 的首页、博客列表和文章页都没有横向滚动。

### 2.3 响应式与动效有工程意识

- 图片普遍声明宽高或固定比例，没有发现明显的无尺寸图片布局跳动风险。
- 雪花会在后台页签暂停；Intro 在 `prefers-reduced-motion` 下跳过；全局 CSS 会压缩动画时长。
- SPA 切页后播放器保持状态、歌词本地托管、评论分页等上一轮实锤问题已经修复。
- 本轮线上抽测页面均返回 200，没有控制台错误；`npm run build`、`npm run check`、`npm run lint` 可通过。

## 3. 优先问题

### P0：320px 小屏存在 20px 横向溢出

**证据**

- Playwright 在 `320×568` 首页实测：`documentElement.scrollWidth = 340`，比视口宽 `20px`。
- 375px、768px、1440px 没有同类溢出。
- 首页 Hero 使用 `width: 100vw` 配合负外边距，全局 `html { overflow-x: hidden; }` 会把问题裁掉，但没有消除几何溢出。

**影响**

- 320px 设备或分屏窗口可能出现内容被裁、横向拖动手感异常。
- `overflow-x: hidden` 会掩盖根因，使以后新增组件时更难定位。

**建议**

- 优先检查首页 Hero 的 `100vw + calc(50% - 50vw)` 组合，在窄屏改为 `width: auto`，用容器外扩或 `100dvw` 的单一方案实现全宽。
- 增加 320px 响应式回归断言：`document.documentElement.scrollWidth === window.innerWidth`。

### P0：Live2D 是首页最大的加载与移动端占位成本

**证据**

- 首页实测首轮资源传输约 `6.25MB`；博客列表约 `2.34MB`，文章页约 `2.06MB`。
- 首页最大资源是 Live2D 纹理 `2.12MB` 和模型 `1.19MB`，合计约 `3.31MB`，另有 Pixi / Cubism 脚本。
- 375px 首页 Live2D 固定区域为 `190×260`，占视口面积约 16%；320×568 下仍为 `190×260`，占视口面积约 27%。
- `prefers-reduced-motion: reduce` 下 Intro 会移除，但 Live2D 仍加载完整模型与纹理并显示；其注视与粒子循环仍使用 `requestAnimationFrame`。

**影响**

- 在手机或慢网下，首页人格化装饰比核心内容更早消耗流量与主线程预算。
- 小屏滚动时左下角持续占据较大区域，容易与“现在在做”、卡片和 Footer 产生视觉争夺。
- 用户选择减弱动效后，仍承担 Live2D 的资源和持续动画成本，偏离该偏好的实际含义。

**建议**

- 移动端默认折叠为 48-56px 的角色头像/徽章，用户点开后再加载 Live2D；桌面保留当前完整看板娘。
- Live2D 改成空闲加载：`requestIdleCallback`、Hero 稳定后加载，或首次交互时加载。
- 在 `prefers-reduced-motion: reduce` 和 `Save-Data` 下不加载 Pixi、模型与纹理，显示静态图即可。
- 为粒子、注视 RAF 增加 `document.hidden` 暂停与组件销毁清理。

### P1：移动端文章目录出现在正文之后

**证据**

- `article-layout` 的 DOM 顺序是正文在前、`aside.toc` 在后。
- 375px 时网格改为单列但不调整顺序。在本次 6505px 高文章中，正文从约 `y=764` 开始，目录按钮在约 `y=5197` 才出现。

**影响**

- 长文读者在最需要目录的开头看不到目录，读完整篇后才遇到入口。
- 桌面端优秀的 sticky TOC 在移动端几乎失去导航价值。

**建议**

- 最小改动：小于 1080px 时给 `.toc { order: -1; }`，把折叠目录移到正文前。
- 更好的移动体验：文章标题下放一个紧凑的“目录”按钮，打开底部 Sheet 或 Popover；保持滚动位置，不建立嵌套滚动区。
- 展开后同步 `aria-expanded`，关闭后把焦点还给触发按钮。

### P1：触控目标偏小，尤其是 Header 与 Live2D 开关

**证据**

- Header 游客头像和主题按钮为 `38×38`；桌面 GitHub 按钮也是 `38×38`。
- 首页“今日箱曲”高度约 `41px`，滚动提示约 `42px`。
- MusicDock 歌词按钮为 `30×30`、播放按钮 `40×40`。
- 手机 Live2D 的 `YUKI / OWN` 按钮实际约 `31×12` 和 `32×12`，远低于 44px 触控目标。

**影响**

- 手机端误触概率增加，尤其是靠近屏幕边缘的主题按钮和模型切换。
- 视觉尺寸可以保持小，但当前点击热区也跟着小。

**建议**

- 视觉图标不必放大，把按钮盒统一扩到至少 `44×44`；Live2D 开关用伪元素或 padding 扩大热区。
- Header 在 320px 已很紧，不建议把所有可见圆形都放大；可通过减少空隙、合并次级动作或使用透明热区满足触控要求。
- 把 `44px` 设为交互令牌，例如 `--tap-min: 44px`，覆盖 Header、播放器、目录和评论区按钮。

### P1：缺少统一的 `:focus-visible` 设计与跳转正文入口

**证据**

- 全站样式表实测 `:focus-visible` 规则数量为 0，只有资料页局部规则。
- Tab 导航可到达 Header 和主要 CTA，但主要依赖浏览器默认 `1px auto` outline。
- 输入框存在 `outline: none`，聚焦只改变边框颜色。
- 页面没有 “跳到正文” skip link。

**影响**

- 默认焦点在卡面 Hero、暗色模式和复杂背景上不一定稳定可见，且与站点视觉体系割裂。
- 键盘用户每页都要先穿过品牌、四个导航项、头像和主题按钮。
- 只改变输入边框颜色，对低视力用户不够明确。

**建议**

- 全局增加高对比 `:focus-visible`：2-3px 外环 + offset，亮暗主题分别验证。
- 恢复输入框 outline 或使用双层 box-shadow，不要只靠边框变色。
- `<body>` 开头加入默认隐藏、聚焦后显示的“跳到正文”链接，并给 `<main id="main-content">`。

## 4. 次级优化

### P2：文章与博客列表缩略图全部是空 alt

**证据**

- 博客列表 featured / card 的 `heroImage` 使用 `alt=""`。
- 文章页 Hero 同样使用 `alt=""`。

**判断边界**

- 如果图片只是标题的装饰性封面，空 alt 是合理的。
- 如果图片展示项目界面、错误现象或文章关键结果，空 alt 会丢失信息。

**建议**

- Content schema 增加可选 `heroImageAlt`；纯装饰时留空，有信息时由文章作者填写。
- 不要自动把文章标题原样塞进 alt，那只是重复朗读。

### P2：首页首屏同时存在过多“主角”

源码层面同屏有 Hero 文字、双 CTA、玩家档案、今日箱曲、滚动提示、雪、Live2D、音乐 Dock。每个单独看都合理，但在小屏上会竞争注意力。

建议采用设备分级，而不是删掉特色：

- 桌面：保留完整 Hero + Live2D + Dock。
- 平板：Live2D 缩小或延迟出现。
- 手机：首页首屏只保留 Hero、主 CTA、玩家身份；今日箱曲和 Live2D 进入首屏后半段或折叠入口。

### P2：音乐电台的关闭状态可以更轻

- 关闭时真正可见的是 46px 圆形按钮；Playwright 返回的 `320×129` 是包含隐藏面板的父级布局包围盒，不应误判为整块遮挡。
- 但歌词按钮 `30×30`、来源切换和曲目小胶囊仍偏密集，手机打开完整歌词面板后需要专项验证单手操作。

建议优先扩大热区，再考虑把完整歌词改成手机底部 Sheet；桌面继续使用当前 Dock。

### P3：Footer 信息密度较高

Footer 同时承担横幅、波纹、星点、快捷导航、技术标签、运行时间、版权和长素材声明。它符合粉丝站气质，但移动端尾部较长。

建议保留横幅和版权，把技术标签或详细素材声明改成可展开区；这属于风格取舍，不是必须修复。

## 5. 不建议做的改动

- 不建议改成通用黑白极简博客。那会提升“模板式整洁”，但直接损失这个站最有价值的识别度。
- 不建议删除霞鹜文楷、真冬紫、卡面 Hero、音乐电台。应优化加载时机和设备呈现，不是抹掉人格。
- 不建议给基础交互增加“点击这里”“点击头像”等解释文案。现有用户契约要求靠清楚的状态、热区和反馈解决问题。
- 不建议为了 44px 目标把 Header 视觉元素全部放大；应扩大点击盒、调整密度或收纳次级操作。

## 5.1 本轮实施取舍

- 已实施：320px 溢出、移动目录前置、全站焦点与跳转正文入口、关键按钮触控热区、可选 `heroImageAlt`。
- 经用户确认不实施：Live2D 折叠、懒加载或减弱动效静态化。看板娘的加载与移动端占位保持现状。

## 6. 建议实施顺序

| 顺序 | 改动 | 预期收益 | 成本 |
|---|---|---|---|
| 1 | 修 320px 横向溢出并加回归断言 | 消除确定的响应式缺陷 | 低 |
| 2 | 移动端目录前置 | 长文导航立刻可用 | 低 |
| 3 | 全局 focus-visible + skip link | 键盘可达性完整一档 | 低 |
| 4 | Header / Dock / 文章目录扩大点击热区 | 降低手机误触 | 低到中 |
| 5 | Live2D 手机折叠、懒加载、减弱动效静态化 | 首屏流量、性能和内容空间明显改善 | 中 |
| 6 | heroImageAlt 数据字段 | 内容语义更准确 | 低 |
| 7 | 手机首屏减法、Footer 收纳 | 进一步提升信息层级 | 中，含审美取舍 |

## 7. 验证数据

- 线上状态：首页、博客列表、文章页均为 HTTP 200。
- 视口：320×568、375×812、768×1024、1440×900。
- 横向溢出：320px 首页 `+20px`；其余抽测视口 `0px`。
- 资源传输：本次环境首页约 `6.25MB`，博客列表约 `2.34MB`，文章页约 `2.06MB`。这些是 Playwright Performance Resource Timing 的单次传输值，不等于 Lighthouse 总分，也不代表所有网络环境。
- 最大首页资源：Live2D 纹理约 `2.12MB`、模型约 `1.19MB`、默认曲绘约 `0.72MB`、Footer 横幅约 `0.51MB`。
- 代码门禁：`npm run build` 成功构建 14 个页面；`npm run check` 为 0 errors、0 warnings、2 hints；`npm run lint` 退出码 0。
- 回归脚本：`blog/tests/ui_ux_regression_v2.py`，可针对本地预览或生产域复跑。

## 8. 局限

- 本轮没有使用图像理解能力，所以不对“角色脸部裁切是否最好看”“卡面色调是否协调”这类纯视觉问题作伪判断。
- 没有跑 Lighthouse / Web Vitals 实验，不把资源体积直接等同于 LCP、INP 或性能评分。
- 未登录状态下完成评测，未覆盖登录后头像菜单、个人资料和评论发布完整流程。
- `se_0248_01.mp3` 在页面初始化时出现 `net::ERR_ABORTED`，更像媒体预加载被浏览器取消；本轮没有把它定性为用户可见故障。
