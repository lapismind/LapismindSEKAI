## 起因

一开始其实就是给纳塔打了个洛茜的 mod。人物换好了，一听语音还是原来那个，怎么听怎么别扭——穿帮就穿在声音上。

想着配套把语音也换掉，就去找现成的语音包，翻了半天没找到合适的。找不到那就自己做。

做法是拿角色原版台词当参考，用 **Qwen3-TTS-12Hz-1.7B-Base** 克隆声线，再说出任意中文 / 日语台词。干员原版语音本来就是最贴角色的素材，比任何"合成音色"都准。

这就是 `tts-studio` 的起点。当时当然没想到，它会一路长成现在这个样子。

## 先讲清楚：声音克隆在干嘛

它的输入是三样东西：

```
参考音频（一段角色原版台词）+ 参考文字稿（这段台词的原话）
    ↓  Qwen3TTSModel.create_voice_clone_prompt()
声音特征
    ↓  generate_voice_clone(要合成的新台词, 语言, 声音特征)
新的音频
```

关键点是**两个输入必须对齐**：给模型听的音频，和告诉它"这段话是这个字"的文字稿，得是同一句。对齐了它才能把音色和发音拆开，用音色去读新内容。

所以整个项目的一半工作量，其实不在模型上，在**素材**上——得先有一份干净的、音频和文字逐条对上的数据集。

## 数据从哪来：抓 PRTS 的三个坑

第一个角色是洛茜，数据来自终末地 WIKI；第二个是澄闪，数据来自 [PRTS 明日方舟中文 WIKI](https://prts.wiki)。抓取脚本 `scrape_prts_voice.py` 只用 Python 标准库，对任意干员通用。

看起来是"下载页面上的音频"，实际上一路都在解谜。

**1. 页面上根本没有音频直链。**

PRTS 的语音表是前端组件渲染的，源码里只有数据属性：

```html
<div id="voice-data-root"
     data-voice-key="char_377_gdglow"
     data-voice-base="日语:voice/char_377_gdglow,中文-普通话:voice_cn/char_377_gdglow,…">
```

真正的地址是前端 JS 拼出来的 `https://torappu.prts.wiki/assets/audio/{voiceBase}/{文件名}.wav`。这里有两个小坑：文件名**必须转小写**（`CN_001.wav` 的实际资源是 `cn_001.wav`，照 HTML 里的大小写拼就是 404），而且 `voiceBase` 已经带了干员代码（`voice_cn/char_377_gdglow`），别再拼一次。

**2. WAF 会把默认请求头挡掉。**

Python `urllib` 默认发 `Connection: close`，PRTS 直接 403。得把 `Accept`、`Accept-Language`、`Connection: keep-alive` 补上才拿得到页面。

**3. 立绘地址比语音更藏。**

干员页里内联的 `charimg_params` 里 `url` 字段是空的，真实地址由 charinfo 应用运行时算出来。我没去逆它的哈希算法，而是顺着 `getPath(...)` 的调用点读出命名规则，再问 MediaWiki 的 `imageinfo` API 要真实地址，顺带把宽高也拿回来。

这里栽过一个记不住的跟头：**MediaWiki 会把标题里的下划线规范化成空格**。我问"立绘\_澄闪\_1.png"，它回来的是"立绘 澄闪 1.png"，键名不换回来就一个都对不上。更阴的是时装名只存在于干员主页，不在 `/语音记录` 子页——我一开始拿子页去解析，结果时装候选全空，而代码是"静默 `continue`"跳过的，问题被藏住了。现在它会明确打印「PRTS 上存在 N/M 个候选」和缺失清单。

抓下来的成果：

| 干员 | 来源 | 中文 | 日语 | 立绘 |
|---|---|---|---|---|
| 洛茜 | 终末地 WIKI | 82 条 | 82 条 | 18 张 |
| 澄闪 | PRTS 明日方舟 WIKI | 38 条 | 38 条 | 8 张 |

立绘 PNG 合计 18MB，加 `--art-webp` 转存后 **4.1MB（约 1/4.4）**，尺寸不变。

## 参考音频不是越长越好

这是移植到任何声音克隆项目都用得上的一条。

Qwen3-TTS-Base 的参考音频过长会**克隆卡死**，官方建议 3 秒左右。可干员的台词经常十几秒，怎么办？

切。但不是随便截断——`ref_split.py` 按标点找句子边界、对上音频里的静音中点，只保留切点**之前**的完整句子。澄闪数据集里第 001 条中文是 8.1s、日语是 11.5s，日语那条会被切成第一句约 5.3s（洛茜的 001 只有 3.7s，不用切）。

这里有一条不能破的规矩：

> **音频和文字稿必须同时截断，绝不出现"文字稿比音频长一截"。**

那等于让模型去复述它根本没听到的内容。遇到第一句本身就超长的（比如「生日」28.7s），就按时间比例同时截音频和文字稿；纯标点碎片（「……」「。」）并回前一句，免得把比例估算带偏。

还吃了一个类型坑：`prepare_reference()` 不切分时返回的是**路径字符串**，切分后返回 `(数组, 采样率)`，但绝不能直接传 `Path` 对象——模型会报 `Unsupported audio input type`。

## 让机翻说人话：词典 + 口癖

中文台词好办，日语才是主战场。本地跑 NLLB-200-distilled-600M，管线是这样的：

```
官方台词直查（与官方日文完全一致时零机翻）
  → 术语前替换（中文词先换成官方日文写法）
  → NLLB 分句翻译（长句切短）
  → 误译纠正（variants）
  → 全角标点清理
  → 干员口癖优化
```

每一步都是踩出来的：

- **必须分句翻译。** 长句整段塞进 NLLB 会丢词丢句，得按 `。！？，；、…` 切短再翻，每 8 句一批——38 行台词能切出上百个短句，一次全塞进去会把 12G 显存撑爆。
- **NLLB 会复读。** 长口语句上会退化成「ほら ほら ほら…」「田舎の田舎の…」。实测 12 条最长台词，不加 `no_repeat_ngram_size` 退化 **3/12**；设成 5 之后 **0/12**，输出长度比从 1.21 降到 0.97，速度还快 3 倍。
- **纯标点不能进模型。** 单独一个「……」送进去，模型会凭空编出「私は..。」再拼回句子里。现在无汉字/假名/字母数字的片段直接原样保留。

### 口癖必须按角色分，套反了会把语气改回去

这是我最有成就感、也最不敢省的一步。两个角色的说话方式正好相反：

| | 洛茜 | 澄闪 |
|---|---|---|
| 自称 | アタシ 38 次 / 私 1 次 | 私 16 次 / アタシ·僕 0 次 |
| 语气 | 常体（だよ／ないよ） | 敬体 です・ます 40 次，句尾常体 0 次 |
| 称玩家 | —（叫管理人） | ドクター 15 次，从不出现 あなた／君 |
| 特征 | あの／えっと／その 15 次 | 「〜んです」13 次 |

所以规则按干员名选，**不能共用**。拿澄闪 38 条官方台词做对照，官方日文当基准：

| | あたし／アタシ | あなた／君 | ドクター | 句尾常体 | です／ます |
|---|---|---|---|---|---|
| 官方日文（基准） | 0 | 0 | 15 | 0 | 40 |
| 纯机翻 | 0 | **6** | 9 | **3** | 22 |
| 词典 + 澄闪口癖 | **0** | **0** | 16 | **0** | 30 |

机翻原本会冒出 6 次「あなた／君」、3 处句尾常体，套上 profile 后归零，称呼和敬体都贴近官方。这组数字是改规则时的回归依据，每次动 `_stylize_chengshan` 都要重跑一遍。

术语表则是另一层。明日方舟组的 41 条是对着澄闪官方日文台词逐条核对过的：源石技艺→アーツ、法杖→アーツユニット、电荷→電気。有些歧义太大的**故意没收**，比如 アース→アーツ（"接地"在日语里就是 アース）、医者→ドクター，怕误替换反而伤到正常译文。

词典所有干员共用一份，内置明日方舟 41 / 终末地 7 / 怪猎荒野 69 条，加上自定义的 785 条，改完不用重启，翻译时热生效。

需要说清楚的边界：NLLB-600M 对长口语还是会出错译，**建议把译文当草稿手改后再合成**。只有和官方台词完全一致的行才会零机翻直接命中。

## 两个项目收成一个

项目做到一半，我发现自己手里有两个目录：`洛茜` 和 `澄闪`。

它们本质是同一个项目的两代实现——洛茜那版是单干员硬编码，澄闪那版泛化成了多干员。结果就是环境归属不清、词表分两处靠跨项目只读共享、两份 AGENTS.md、两个入口 bat，同名文件还有各自漂移的风险。

于是决定合并。以泛化版为唯一实现，洛茜降级成"第二个数据集"，整个项目改名 `tts-studio`。

合并里最实在的一条经验是 **venv 不能直接乱搬**：`Scripts\pip.exe` 这类启动器内嵌了旧的绝对路径，搬完得 `pip install --force-reinstall pip` 重建启动器（`python.exe` 本身靠相对路径的 `pyvenv.cfg`，不受影响）。搬完先跑 `--check` 看 `cuda_available=True` 才敢继续。

## GUI 重写：把重活赶出界面进程

第一版 GUI 是 961 行 tkinter，问题很典型：

- **单进程混合**：模型加载、合成、翻译全在 GUI 进程里跑，引擎一崩界面一起崩；`ref_split` 依赖的 librosa/numpy 被顶层 import 拖进来
- **两份平行实现**：GUI 里一套合成循环，命令行里又一套，命名已经开始漂移
- **零状态持久化**：窗口大小、干员、语言、参数每次启动全重置

重写成了 **PySide6 + QFluentWidgets**，核心是**双进程**：

```
启动 bat / 快捷方式
  └─ 全局 Python: gui_fluent.py      ← GUI 进程（PySide6，零重依赖）
        │ stdin  → JSON 行命令
        ├────────► .venv\python engine_worker.py   ← 引擎进程（独占 torch / NLLB）
        │ stdout ← JSON 行事件
        ◄────────
        │ stderr ← 第三方日志 → GUI 日志面板
```

好处很直接：GUI 进程不 import torch 就不加载，起得快、也崩不了；引擎按需启动（第一条合成/翻译命令才拉起）、空闲 600 秒自动退出、崩了下次命令自动重拉。合成内核抽成 `engine.py`，worker 和命令行共用同一份，消灭了两套实现。

中间有一个隐蔽但要命的问题：**worker 的 stdout 是协议通道，绝不能被第三方库的 print 污染。** qwen_tts 和 transformers 的 import 警告、进度条都会往 stdout 写，一行混进去协议就解析错了。

解法很干净，在 worker 入口前几行把 fd 换掉：

```python
import os, sys
_proto = os.fdopen(os.dup(1), "w", encoding="utf-8", newline="\n")  # 协议独占 fd1 的副本
sys.stdout = sys.stderr                                             # 之后所有 print 改道 stderr
```

协议从此走 fd1 的副本，别的一切输出落到 fd2，由 GUI 的读线程收进日志面板。顺带把界面风格也定了：用户指定**终末地工业**基调——石墨蓝深底、琥珀 `#f5c445` 作核心亮色、分区标题做成设备铭牌、状态栏做成设备指示灯，顶栏叠一层低透明度等高线。

## 写在边界上的话

- PRTS 只列**游戏里有音频的**语音。澄闪抓到 38 条，因为游戏内序号 1~44 本身就跳号。
- 日语第 37 条「生日」在 PRTS 上是漏翻的（日文栏直接填了中文），数据集里标了 ⚠，**不能当参考音频**——拿中文文字稿配日语音频，模型学到的就是错的。
- 半身像是游戏内小尺寸图（180×360），放大看会糊；要高清得用「立绘\_」开头的那批。
- `flash-attn` 没装，走 PyTorch 手动注意力，加载时会有警告，可以忽略。
- 中→日翻译只对日语合成有意义；目标语言选中文时翻译按钮直接禁用。
- **原版语音版权归鹰角网络所有，本项目仅用于个人研究。**

## 最后

回头看，这个项目最花时间的从来不是"跑通模型"——那可能只占两成。剩下八成都在把素材弄干净：抓得对、切得准、文字稿和音频严格对齐、翻译别把角色的语气改反。

模型给了你一个能模仿声线的能力，但它不会替你去核对第 37 条台词是不是漏翻了，也不会告诉你洛茜说的是アタシ而澄闪说的是私。**这些才是"像不像"的分界线。**

给 mod 里的洛茜配上声音这件事，最后做成了一个能切换任意干员的工作台。现在就差把新的角色一个个加进去了。
