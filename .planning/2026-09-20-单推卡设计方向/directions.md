# 单推角色卡（`.oshi-card`）· 设计方向提案

> 提出者：视觉设计总监视角
> 日期：2026-09-20
> 性质：**纯设计提案**。除本文件外没有改动任何源码、素材、配置；没有 commit、没有部署。
> 起因：用户评「**我感觉这样还是太平庸了，只是普通图片和文字环绕。我们有最好的生图模式，现在只差样式设计了。**」
> 前提：**生图不是瓶颈**（文生图 + 图生图编辑，模型 image2.5，已用过上百次）。所以本文件不写"图能不能做出来"，
> 只写"想不想得出来"，以及"做出来后亮/暗、手机、体积、可访问性怎么过"。

## 1. 诊断：「平庸」的确切机制

不是"排得不够整齐"——**恰恰相反，现在这版是同尺寸下排得最整齐的一版**。问题在于这张卡的**设计动作只有一步**，
而这一步是**给文字减宽**。逐条说：

### 1.1 图对版式的全部影响，是一个 CSS 变量

```css
.oshi-card { --oshi-art-w: 320px; grid-template-columns: minmax(0,1fr) var(--oshi-art-w); }
```

源码注释自己写得很诚实：「版式以作画为先：右侧一整列留给真冬半身像，文字列自适应收窄」，以及
「实测：文字列约 357px 时 `.oshi-facts` 的 auto-fit 会自己从三列变两列，所以"资料让位"这件事不用手写断点」。
——**这就是"图 + 环绕文字"的数学定义**：画面进来，只导致文字**重新折行**。它没有改变文字的**形状、顺序、
等级、位置、时间**中的任何一项。文字的排版逻辑在加图前后是同一套，只是量尺从 700 变成了 355（实测 355.0px）。
一张漫画分镜和一列自动 fit 的网格，差别不在整齐度，在于**谁决定了谁**。这里始终是网格决定画面：**卡片的形状先定，
图被裁进那个形状**（见 1.4）。

### 1.2 八项等权 = 没有信息等级 = 没有观点

实测桌面端 `.oshi-facts`：355px 宽 → `auto-fit` 出 **2 列 ×166px、4 行 ×69px（合计 310px）**，八项**视觉重量完全相同**。
于是「**不擅长：表达情绪**」——整个数据集里唯一一句人物性格——与「**身高 162cm**」获得同样的字号、同样的颜色、
同样的行距、同样的邻接关系。这不是排版问题，是**判断缺失**：一个真的单推她的人不会这么写。
卡里的主题句与签名句同样只是两段尾巴，不是版面的支点。

### 1.3 装饰是"占位符"的形状，不是设计的形状

- `.oshi-moon`：420×420 的径向渐变光斑，锚 `top:-92 right:-104`，**靠卡片的 `overflow:hidden` 裁掉外侧**。
  实测桌面端就是 420×420，位置正好压在"人物头部该在的地方"。
- `.oshi-snow i`：6 个 CSS 圆点当落雪，`animation: snow-fall linear infinite`。

这两个东西的存在只为填满右列；代码注释也承认"作画槽"。**暗色主题下全卡最显眼的东西是一颗 420px 的灰白球**
（见 03 号截图），亮色主题下它几乎不可见——也就是说**两个主题连构图都不是同一张**。
占位符的第二个证据：它们没有任何一处与文字发生关系（月亮的圆心、雪点的落点、文字的对齐线，三者互不相干）。

**顺带一个实锤缺陷**：`.oshi-snow` 的 6 个无限动画**没有 `prefers-reduced-motion` 兜底**，
而站点自己的全站 canvas 细雪是有的（`site-features.md` §2「`prefers-reduced-motion` 停用」）。
即这张卡在"尊重减弱动效"上**低于站点自己定的标准**。这是现状的既有问题，任何新方案都应顺手修掉。

### 1.4 两个主题不是"两个状态"，是"两套配色"

`:root[data-theme='dark'] .oshi-card` 只改了一个 `background`（两段 OKLCH 渐变），
外加月亮和雪点的颜色。**同一张构图，换了两组色号。** 亮与暗在**设计层面是同一个东西**——
所以用户按下那个开关，得到的是一次"变暗"，而不是一次"看到别的什么"。这是"平庸"里最贵的一条：
站点已经给了一个**免费的交互**（主题开关），卡片对它是**零响应**。

### 1.5 作画槽这个形状本身是坏的（连图都被它连累）

320 可见宽 × 565 高 = **1 : 1.77**。3:4 的半身像放进 1:1.77 的竖条里，**宽度要丢掉约 40%**——
上一轮 A1 的规格文档里其实已经算到了这一步（"900×1200 里真正入画的只有左侧 2/5…否则裁切后会只剩一只胳膊"）。
也就是说：**版式是先定的，图是被裁剪去适配版式的**。这让"生成一张好图"这件事先天吃亏。

### 1.6 手机端的代价（实测）

| 视口 | 卡片高 | 资料块 | 资料块怎么排 |
|---|---|---|---|
| 1440 | 703 | 310 | 2 列 ×166，4 行 ×69 |
| 390 | **1025** | 339 | 2 列 ×134；第一行 98（"1 月 27 日 · 水瓶座"折了行） |
| 320 | **1415** | **631** | **退化成 1 列 ×220，8 行 ×69**；整页 4573px，`main` 3496px |

320 下每项资料占 69px，是因为 `.oshi-fact` 把 `k`（生日）与 `v`（1 月 27 日 · 水瓶座）**分成上下两行**。
这一项**光是把 label 与 value 并排就能省下约 330px**（8 项 ×69 → 8 项 ×约 28）。这是任何方向都该顺手吃到的收益。

### 1.7 一句话

> **现在这张卡的每一个元素都在正确的格子里，但没有任何一个元素在决定另一个元素。**
> 图只改了一个列宽数字；八项等权，于是"不擅长表达情绪"和"162cm"一样重；
> 装饰是等着被替换的占位符；主题开关只改色号；作画槽的形状连图都放不好。
> 它不是排得不好——**它是没有主张**。

而现状是文字被作画列压到 355。

**风格参照（看过的页面，用于"新图要与谁共处一站"）**：
- `/` Hero = 官方卡面（教室 + 钢琴 + 真冬/奏）+ 重青色渐变洗底 + 居中大字。
  → **站内已经有一个"全幅底图 + 文字压在上面"的习惯用法**，所以"把这张卡做成小 Hero"是**贬值**而不是升级。
- `/projects/` = 每张封面一个大圆角矩形、文字在下方；`/works/`、`/blog/` 同族。
  → **站内的通用语汇就是"图放框里、文字在旁边/下面"**，所以单推卡越接近它，越像列表里的一个条目。
- `/about/` 其余三块（玩家档案卡 / 现在在做 / 技术栈）都是"玻璃卡 + 左对齐文字"。
  → 单推卡是**全站唯一有真实主角**的一块，它有权用**别的语言**说话。
- 原创素材家族：三张游戏封面（深紫夜 + 暖灯，半写实厚涂；出包那张最终版是暖调室内群像）、
  页脚 MMD 平涂 chibi 五人横幅（黑底）、`mascot.webp` 平涂 chibi 头像（黑底，大块实心、无渐变）。
  → **"平涂 + 大块实心 + 单一光源"在站内已经被接受过两次**（mascot / 页脚），是最安全的新图语言。

## 3. 方向 A ——「水槽 / 空的水槽」★推荐

### A.1 概念一句话
**这张卡不是卡片，是一只水槽：资料浮在水面上，她的心事沉在水下——而切换主题就是镜头入水。**

素材来自她本人：趣味是**水族箱**、网名「雪」、深夜在线、不擅长表达情绪、
主题句写的就是"在夜与雪之间"。水是唯一一个能同时装下"雪 / 水族箱 / 深夜 / 说不出口"的物理。

### A.2 为什么它不是「图 + 环绕文字」
- **画面没有边界，因此没有"旁边"**。卡面本身就是水（由令牌推导的背景，不是"贴上去的图"）。
  不存在"作画列"这个盒子，也就没有可以并列的两个矩形。
- **画面重新排序了文字。** 一条水面线横穿整张卡，它是**版式法则**而不是装饰：线上放 6 项可量化的资料
  （生日 / 年龄 / 身高 / CV / 趣味 / 擅长 / 喜欢的食物），线下放三项"说不出口的东西"
  （**不擅长 表达情绪** / 主题句 / 签名句）。**事实浮着，心事下沉**——八项统一的等级被打散成两个高度层。
- **文字有两个深度。** 线上文字在画之下（她的肩可以压过它），线下的主题句在画之上（压在她的身体上）。
  于是文字**穿过**画面，而不是绕开画面。
- **主题句有水中的倒影**（`scaleY(-1)` + 模糊 + 低不透明度）。**倒影是把文字交给画面的最直接手法**：
  一份文字出现两次、第二次是画面的一部分，读者不会再把它读成"一段配文"。
- **时间**：水面在动、波光在动，倒影跟着晃。这是安静的、连续的、与她的存在有关的时间，
  不是现在那 6 个无来由的圆点。

### A.3 图怎么用
- **1 张，透明 WebP**（约 700×1100 源，3:4 竖构图）：腰以上、侧身、双臂自然垂或一只手向上轻伸、
  **脸朝左上（朝水面），不与镜头对视**，半睁眼、无笑容。她**从水下向上浮，头肩穿过水面线**。
- **跨水面由 CSS 完成，不要求模型理解"半身在水里"**（这是模型最难画准的事）：
  同一张图渲染**两层**——
  - 水上层：原图，`clip-path: inset(0 0 <水面线以下> 0)`；
  - 水下层：同图同位置，`clip-path: inset(<水面线以上> 0 0 0)` + `filter: saturate(.65) blur(1.5px) brightness(.94)`；
  - 两层中间压一条 2–3px 的高光带（水面）+ 一条 8px 的柔化带，把层间的滤镜落差**变成水面本身**。
  这两层共用**同一个变量 `--oshi-wl`（水面 y）**，而资料的分组、水色渐变的分界也读同一个变量。
  **一个变量驱动三件事，所以它们不可能走样。**
- **透明通道怎么来**（若模型不能直出 alpha）：**纯色键控底 + 硬边**
  ——提示词写死"纯单一绿色 `#00FF00` 平涂底、无渐变、无投影、无环境光溢出"，
  另外要求"**发束是整块的实心色块，最多三档明暗，不要散开的细发丝**"。
  这一条同时解决两件事：硬边让键控干净（不会留灰边），且符合站点既有的平涂语言（mascot / 页脚馒头人都是大块实心）。
  去背用 Pillow 一次性脚本（确定性、可复跑），**不要用需要下载权重的模型**。
- **若透明最终拿不到**：退成**两张带底图**——亮色主题一张"高调水色（像白天看水族馆，浅青白）"、
  暗色一张"深水（深紫蓝）"，都是 3:4 满高、从卡的右缘与下缘出血。代价：+1 张图，但版式完全不变
  （因为水的分层本来就是 CSS 层，不依赖图的背景）。

### A.4 文字与资料如何参与构图

| 内容 | 去哪 | 说明 |
|---|---|---|
| 姓名 + 日文名 | 水面之上，卡的左上 | 现状字号即可，压在"灯光照到的水面"上 |
| 单元名徽章 | 水面之上 | 现状那颗胶囊保留（它已经是站内语汇），但底色改为"水面"的浅色 |
| 6 项资料 | 水面之上，**保持网格**（可扫读的地基不动） | 文字列从 355 → 约 420–500（她出血更多、不再占一个 320 的盒子），可望变 3 列 |
| **不擅长：表达情绪** | **水面线下第一件事**，字号提一档，前面一个 CSS 画的"下沉气泡"（缓慢上浮） | 全卡最有情绪的一行被从网格里救出来 |
| 主题句 | 水下，大字（`clamp(1.35rem,2.6vw,1.9rem)`），**带水平镜像倒影** | 倒影 `aria-hidden="true"`，不重复给读屏 |
| 签名句「谢谢你，找到了我。」 | 主题句正下方，等宽小字 | 像水底的一行题词 |
| 版权小字 | **卡的最下缘**（水底），横排满栏 | 对比度按 `--muted` 一档处理，仍 ≥4.5:1 |

- **DOM 与语义**：顺序做成「姓名 → 6 项资料 → 不擅长 → 主题句 → 签名句 → 版权」，
  **视觉顺序 = DOM 顺序 = 读屏顺序，三者一致**。资料仍是定义列表语义（`<dl>` 或现有结构 + `k`/`v` 类名）。
  搜索 "162cm"、"田辺留依" 照样命中（都在 DOM 文本里）。**这是四个方向里 a11y 风险最低的一个。**
- **分时**：不依赖交互就成立。可选加法：`@media (hover:hover)` 下她所在区域被 hover 时水面高光更亮一点
  （纯装饰，不承载信息）。

### A.5 亮 / 暗双主题
- **亮 = 白天的水族馆**：水面之上是 `--primary-ghost` 系的极浅紫白（灯照在水上），
  水下是极浅的冷青白（`oklch(0.90 0.03 243)` 一类，仍在站点冷调家族内）。她正常受光。
- **暗 = 你就在水里**：**水面线移到卡片上缘之外——整张卡都在水下**。水色走 `--primary-ghost` / 深紫蓝两档，
  她的光改由**一条从上方水面漏下来的光柱**承担（`clip-path` 多边形 + 低透明渐变，**只此一处发光**，
  符合上一轮"发光密度是最重的 AI 味来源、只留一处"的纪律）。
- **这条差异是设计的一部分，不是两套配色**：亮色是"你看见她"，暗色是"你在水里，和她同一深度"。
  同一个开关，两个叙事。**这就是"变成有主张的东西"的落点。**
- 顺手删掉 `.oshi-moon`：它是占位符，画来了就该让位（而且它在暗色下是全卡最显眼的东西）。

### A.6 390 / 320
- **390**：水面线保持水平（不要倾斜——倾斜的水面线会和横排的文字打架）。文字单列；
  她在**右上**，用 `top/right` 与她自己的宽度变量锁住水面线穿过的锚点（**让她的眼睛大致在水面线的高度**）。
- **320**：
  - **顺手修**：`@media (max-width: 420px)` 把 `.oshi-fact` 改成 `flex`（`k` 固定 4.2em、`v` 右对齐），
    8 项从 631px 降到约 230px；
  - 新设计的水下部分（主题句 + 签名 + 倒影）对卡高的贡献约 90–120px，但资料省下约 400px，
    **预计 320 下卡高从 1415 降到 约 1050–1150**，390 从 1025 降到约 900。
  - **明确删掉**：现状手机端那个 348×260 的"顶部满宽图槽"。它是"图配文"逻辑的产物，是最该被去掉的一块；
    手机端她改为**右侧出血的窄条**（约 `min(190px, 52vw)`），只露头肩，穿水面线。
- 320 不引入任何横向滚动：她出血的方向是右与上，卡的 `overflow:hidden` 吃掉。

### A.7 性能
- **1 张透明 WebP，目标 ≤55KB**（人物 + 无背景，压缩友好）。走 `src/assets/` + `astro:assets` 的 `Image`
  （内容哈希 → `/_astro/*` 的 `immutable, max-age=31556952`）。**不要往 `public/` 丢裸文件**（那是 7 天陈旧区）。
- **不在首屏**：`/about/` 里这张卡是第 4 个区块（`main` 高 2084px，卡片上方还有玩家档案 / 现在在做 / 技术栈）。
  图必须 `loading="lazy"` + `decoding="async"` + 显式 `width`/`height`（避免 CLS）。
- **CSS 成本比现状更低**：删掉 `.oshi-snow` 的 6 个动画元素与 420px 光斑后，
  新增的只是渐变、`clip-path` 与 `filter`（都是同一个合成层里的便宜操作）。
- 亮暗两套水色是**令牌推导**，不各自出图，零额外体积。
- 若因透明失败退成两张带底图：合计 ≤110KB，仍然懒加载、不在首屏。**诚实说：这是本方向唯一可感知的体积代价。**

### A.8 实现代价与风险
- **改动范围**：只 `about.astro` 的 `.oshi-card` 区块（模板 + 它那个 `<style>`）。
  删 `.oshi-moon`；`.oshi-snow` 要么删、要么补 `@media (prefers-reduced-motion: reduce) { animation: none }`（补上算修 bug）。
  不碰 `/about/` 其他区块、不碰全局、不碰 `profile.ts`。`.oshi-*` 类名全局唯一（已 grep 确认），不会撞 `<style is:global>`。
- **最难一步**：**水色**。要在亮暗两套下同时满足"文字 ≥4.5:1" + "她的肤色不发脏"，需要反复调。
  对策：水色也做成 `.oshi-card` 上的局部变量 `--oshi-water`（亮暗各一档），**只改这一个值就能调**。
- **最可能翻车**：
  1. **透明键控的头发边缘**——对策：提示词要"整块实心发束、最多三档明暗、不要散开的细发丝"（见 §9）；
     若仍有灰边，水下那层本来就要模糊，把灰边留在水下、水上只保留轮廓清晰的部分。
  2. **水下层的滤镜太重 → 像"图没加载出来"**——对策：`blur ≤2px`、降饱和 ≤35%，
     **不要同时降对比**（明暗交界要保留，那是平涂的命）。
  3. **水面线穿过她的脸**——对策：水面线位置写成 `top: calc(...)`（与上方文字块的高度挂钩），
     并且与她图的 `top` 共用变量；验收时专门看一眼 320（水线在窄屏最容易上移）。
- **替代还是新增**：**替代**（换掉现有版式），需要用户拍板。

### A.9 降级版（只做一半）
**一张图都不出，先只做水的结构**：8 项资料按"线上/线下"分成两层、主题句加一份模糊倒影、
删掉月亮换成"渐变水面 + 一条高光线"、`prefers-reduced-motion` 补上。
**零新素材、纯 CSS，约 120 行**。它已经能消掉"两个矩形并列"这件事，而且能**先验证"分层读起来对不对"**
（这是本方向唯一的真问题），再决定要不要出图。**这是我最推荐的动工顺序。**

## 4. 方向 B ——「25:00 的聊天记录 / 别人口中的她」

### B.1 概念一句话
**这张卡是 25 时的群聊：八项资料不是"她的属性表"，而是队友在群里说她的八句话；她本人只发一张照片，和最后那句「谢谢你，找到了我。」**

依据是她的人设本身：单元名就叫「**25時、ナイトコードで。**」，她们在 1 点通过聊天聚在一起；
她的网名是「**雪**」（后来是 OWN）；她**不擅长表达情绪**；她**深夜在线**。

### B.2 为什么它不是「图 + 环绕文字」
- 画面不是"配图"，而是**聊天记录里的一条附件**：它有时间戳、有气泡壳、在**文字的流里**、而不是在文字旁边。
- 它改的是**谁在说话**。同一份数据，从"属性表"变成"关系"——读者读到的不是"她的身高是 162"，
  是"**有人在说她**"。这是四个方向里唯一动"发言主体"的方案。
- **最不能表达情绪的那一项，在界面上表现为"她打了字又没发"**：「不擅长 表达情绪」做成一条
  **虚线气泡、半透明、带"撤回"标记**的消息。这是四两拨千斤：人设直接变成了界面行为。

### B.3 图怎么用
- **1 张，带底横图（3:2）**：深夜房间、桌上只有一台亮着的显示器、她侧对镜头只露一部分脸、
  屏幕光打在一侧脸上、**画质像"手机随手拍"**（略失焦、构图不完美、轻微歪）。
- **另一个资产：0 张**——**不要头像图**。四个队友用**代表色圆点 + 名字**（她 #8888CC）。
  这样零版权增量、零一致性风险，而且**"颜色"本身就是 PJSK 的语汇**。
- **代码合成什么**：气泡、时间戳（`25:00` / `25:03`…，**纯 DOM 文本，绝不让模型画时间数字**）、
  "正在输入…"三点动画、照片的白边框与 `rotate(-0.6deg)`（做出"贴上去"的感觉）、
  最后一条消息后面**一个永不停止的光标 `▍`**——她还在打字。**一个细节胜过十句解释。**
- **这个方向的最大工程优势：完全不需要透明通道**（照片在气泡里，气泡自带边框），
  于是也**完全不存在亮暗融图问题**。

### B.4 文字与资料如何参与构图

| 内容 | 去哪 |
|---|---|
| 单元名「25時、ナイトコードで。」 | 窗口标题栏左侧 |
| 时间 `25:00` | 标题栏右侧（等宽字体） |
| 「作詞・混音担当 · 网名「雪」/ OWN」 | **一次"改名记录"**：`雪 → OWN` 的系统提示行（这条人设事实本身就是可视物） |
| 主题句 | **频道置顶（pinned）**那一行，等宽 |
| 8 项资料 | 8 条消息，由队友发出。措辞写成"说话"，但**每项保留一枚右侧等宽小签**（`生日 · 1 月 27 日`） |
| **不擅长 表达情绪** | **一条没发出去的消息**：虚线气泡 + 半透明 + 「撤回」 |
| 签名句 | 她本人发的最后一条 |
| 版权小字 | 窗口底部一行"系统提示"（最灰的一档） |

- **措辞纪律（最重要）**：按人设分声部（奏温柔、绘名直率、瑞希调侃、真冬本人极少言），
  **只用资料里已有的 8 项事实 + 主题句 + 签名句**，不新增任何设定、不编剧情。
  示例（可直接用）：
  - 奏：「生日是一月二十七号……水瓶座。」
  - 绘名：「162 啊。看着比这高。」
  - 瑞希：「趣味是水族箱～原来你喜欢看鱼啊。」
  - 绘名：「擅长英语会话，这点真的厉害。」
  - 一位「妈妈亲手做的菜。」
  - 奏：「那个……她说她不擅长表达情绪。」（这一条是**别人替她说**的，所以它才是"撤回"状态）
- **DOM 与语义**：`<ol>` 时间线 + 每项 `<li>`；名字 `<span>`、正文 `<p>`、字段签 `<span class="k">/<span class="v">`。
  读屏读到的是完整的句子**且每种字段名都在**——**信息量比现在更大，没有一处丢失**。搜索 "田辺留依" 仍命中。
- **分时**：气泡按 `--stagger`（70ms）逐条淡入，只在进入视口时一次（复用现有 `.reveal` 机制），不循环。

### B.5 亮 / 暗双主题
- **暗色 = 本色**（1 AM 的聊天窗口：深底 + 她的代表色气泡）。
- **亮色 = 白天回看这段对话**：窗口底变浅（`--card-bg` 系），气泡变浅紫/浅灰，不再是"夜"。
  叙事上完全成立（回看 ≠ 当时），而且**气泡是实色块，不依赖背景**，所以两套主题都不会脏。
- **本方向是四个方向里双主题风险最低的**——唯一要处理的是那张照片"在两套主题下都不刺眼"：
  对策是出图时就要求低饱和（并在 CSS 里 `filter: saturate(.92)`），且照片不要纯黑或纯白的边。

### B.6 390 / 320
- **手机端最好的一个方向**：聊天气泡天生单列，窄屏**不损失结构**（不用做任何降级）。
- 桌面把窗口锁在约 `560px` 居中，两侧留白——**这一条本身就把它和其他满栏宽的卡片区分开了**。
- 320：照片走 `aspect-ratio: 3/2` 自适应；字段签换行即可。
  **卡高预计 ~900px（现状 1415）**：因为一条消息的密度高于"`k` 一行 + `v` 一行"。

### B.7 性能
- 1 张 3:2 横图，**≤70KB**，`astro:assets` 出 WebP，`loading="lazy"`。默认不加载任何头像图。
- CSS 只有气泡圆角、一个闪烁光标、一个三点 gif 的 CSS 复刻（`@keyframes`）。比现状的雪点动画更省。
- 不在首屏，无新增首屏成本。

### B.8 实现代价与风险
- **改动范围**：只这一块，但**模板结构改动最大**（要重排成 `<ol>` 时间线），`profile.ts` 可不动
  （把"谁说的"这句写进模板的常量数组里）。
- **最难一步 / 最可能翻车**：**台词写作**。"队友说的话"一旦写得像客服，或者四个人写成一种声音，整个方向就塌了。
  这是唯一的、也是真实的失败点（比生图风险高）。
- **第二风险：做成一个 Slack/Discord 皮肤**（"UI 皮肤感"是天敌）。对策：
  ① 不画窗口的关闭/最小化/菜单图标，**只保留三样：标题栏一行文字、气泡、时间戳**；
  ② **消息直接躺在卡面上，只有照片有框**——不做"整卡一个大方框"。这一步能把"皮肤"变成"排版"。
- **版权/人设**：借用"25 时在 Nightcord 聚会"这一官方设定（属二次创作的常规表达），
  但**不画任何官方 logo、不复刻 Nightcord 的真实 UI 结构**。写进验收。
- **替代还是新增**：**替代**。

### B.9 降级版
**只做两条消息**：把「不擅长 表达情绪」做成"撤回"的那一条、把签名句做成带闪烁光标的最后一条，
其余 7 项**保持现在的网格**。半小时、接近零风险，先试出"对话体"读不读得下去。
读得下去再铺开成完整时间线。

## 5. 方向 C ——「围着她长出来 / 负空间」

### C.1 概念一句话
**把"列"这个概念取消：她的剪影就是文字栏的边界，文字绕过她的轮廓生长。**

### C.2 为什么它不是「图 + 环绕文字」
- **没有矩形了。** 她的头发、肩线、前臂成为 `shape-outside` 的轮廓，正文沿着剪影起伏；
  主题句作为 **pull quote 悬挂在她肩与发围出来的负空间里**（"在夜与雪之间"正好写在那块空里）。
  界是斜的、是弯的——和"一格放图、一格放字"是两种排版语言。
- 版面上**唯一的直线是字号等级**（姓名 → 主题句 → 资料 → 签名），不靠框线分割。
- 谁附着于谁：**文字附着于她的形状**。这在四个方向里是"文字最服从画面"的一版。

### C.3 图怎么用
- **1 张，必须透明**：约 700×1100 竖构图（3:4），人物偏右、面朝左下（朝文字区）、腰以上，
  **左臂向前伸出一小段**（手臂是让文字"绕"起来的关键：它创造一块内凹的负空间）。
- 键控：`#00FF00` 纯色底 + **硬边实心发束**（同上）。
- 合成：`shape-outside: url(cutout.webp)` + `float: right`，配 **`polygon()` 兜底**（约 12 个点就够，
  肉眼几乎看不出是折线）。**兜底很重要**：各浏览器对 `shape-image-threshold` 的 alpha 阈值处理不一致。
- **若透明拿不到**：退成"不透明的她贴着卡右上出血（两条边由卡的边缘吃掉），
  文字绕的是 `clip-path` 在她左侧切出的**内凹缺口**"。可行，但拼接线比透明版明显——所以透明是首选。
- **不需要第二张图**：因为图是透明的、卡面是 CSS 背景，**主题切换时"她在的世界的颜色"自动由令牌给出**。
  **这是四个方向里唯一一个亮暗共用一张图、且完全不需要两张图的方向。**

### C.4 文字与资料如何参与构图

| 内容 | 去哪 |
|---|---|
| 8 项资料 | **降级为一行行"标签 + 值"的连续正文**（不再是网格），约 34–42em 宽，绕她的剪影排 |
| 主题句 | **pull quote**，`clamp(1.4rem, 3.2vw, 2.1rem)`，绝对定位在她肩/发的负空间，与图的位置共用变量 |
| 签名句 | 她视线方向的下方（朝左下的视线终点），等宽小字，像一句批注 |
| 单元名 | **竖排**（`writing-mode: vertical-rl`）贴卡右缘，作为一条纵向细线——竖排是"这不是普通博客"的最省力信号，且日语单元名竖排天生可读 |
| 版权小字 | 卡的最底部一行，横排满栏（不参与构图） |
| 姓名 | 大字，压在右上（可被她的肩轻微压过） |

- **"标签+值"顺带解决手机端过长**：每项约 28px 而不是 69px。
- **可访问性**：`shape-outside` / `float` **只影响视觉**，DOM 顺序与文本不变，读屏与搜索零影响。
  **唯一陷阱**：主题句与姓名若用绝对定位，必须保证**它们在 DOM 里的位置与视觉位置一致**
  （姓名 → 资料 → 主题句 → 签名），否则键盘/读屏顺序会跳。
- **没有交互**。它的取舍就是**不靠时间、靠排版**：这是一张"印刷品"。

### C.5 亮 / 暗双主题
- 最省：图透明 → 卡面颜色跟着令牌走（亮 = 浅紫白，暗 = 夜紫）。
- **唯一要处理的**：她在深底上的**边界**。若出的是黑线稿，暗色会糊。
  对策：提示词要求「**线条是深紫褐而不是纯黑**」+「**人物自带一圈 1–2px 的极浅冷色轮廓光**」
  （这落在"只此一处发光"的纪律内，因为它是轮廓而非环境辉光）。
- 暗色下可给她背后加一层弱径向光（**取代现在的月亮**）；亮色下不加。

### C.6 390 / 320
- 桌面是这个方向的舞台。**手机端必须放弃核心手法**：`shape-outside` 在 290px 宽里会把文字剪得七零八落 →
  `@media (max-width: 780px)` 下 `float: none` + `shape-outside: none`，图退到上方、文字满宽。
- 于是手机的降级是"一张小图 + 紧凑的标签行"，**仍比现状短**（资料 8×28 ≈ 230 vs 现在的 339/631）。
- 320 与 390 同构，`label` 固定 `4.2em` 保证值不被挤。
- **这一条必须提前说清**：手机端只剩降级形态，这是本方向的主要代价。

### C.7 性能
- **1 张透明 WebP，约 40–70KB**——四个方向里最轻（人物 + 无背景，压缩极好）。
- **无动画、无滤镜层、无 `backdrop-filter`**（删掉月亮与雪点后合成层更少）。这是"最省"的一版。
- 不在首屏；`loading="lazy"`。

### C.8 实现代价与风险
- **改动范围**：只这一块，但 CSS 最"技术"（`shape-outside` + 浮动 + 绝对定位 pull quote 要对齐）。
- **风险其实比看起来低**：**绕排只影响观感，不影响可读性**——无论浏览器支不支持绕排，
  文字都能读，只是绕或不绕。**"坏掉也不会塌"**，这是它最大的安全垫。
- **中风险**：**"杂志感"而不是"粉丝站感"**。它的美学是编辑设计，可能显得冷静、专业，而**不够"爱"**。
  这是它的天花板，也是我把它排第三的原因。
- **替代还是新增**：**替代**。

### C.9 降级版
不做绕排，只做两件事：① 资料改成紧凑的"标签 + 值"行；② 主题句做成大字 pull quote 挂在她旁边的负空间
（只用绝对定位 + 共享变量，不用 `shape-outside`）。**这已经是"杂志感"，比现状好一档，且几乎没有技术风险。**

## 6. 方向 D ——「表と裏 / 一个开关，两个人」（过火但有意思的那个）

### 6.1 概念一句话
**站点的亮/暗开关不再只是配色开关：亮色是她给世界看的那一层，暗色是她自己。同一机位、同一裁切、同一套 DOM——只有她变了，文字的坐标一动不动。**

### 6.2 为什么它不是「图 + 环绕文字」
- 因为在这张卡里**文字是常量，她是变量**。观众自己按下开关，看到"同一张卡上的同一个人换了一次脸"——
  卡片从"一张介绍"变成一次**对照实验**。**文字不是被图环绕，文字是量她的那把尺：尺不动，才量得出差别。**
- 它改的是**重要性排序**，而不只是位置：
  - 亮色下「作詞・混音担当 · 网名「雪」/ OWN」全显示；暗色下**只留「雪」/ OWN**——
    职称是给别人看的，网名是她自己的。
  - 「不擅长：表达情绪」在亮色下是表格里的一格；**在暗色下变成整卡最大的一句话**（同一个字符串，
    在两个主题里占不同的字号与位置）。
  - 两条都只用**已有数据**改变等级，**不新增、不改编任何设定**。
- 与现状的决定性差别：现在两个主题只换背景色（**两套配色**），这里两个主题是**两个人**。

### 6.3 图怎么用
- **2 张，同机位 / 同裁切 / 同比例（3:4 竖）**。这一点是整个方向的成败关键：
  **两张图必须能精确叠合**，否则切换时会"跳"。
- **亮（表）**：白开衫的她，明亮的教室/窗边，**端正、克制的浅笑（营业笑容）**，光线平，背景虚化成明亮白灰。
- **暗（里）**：**同一姿势、同一裁切**，同样的白开衫，但夜里、只有屏幕/月光从侧上方打过来，
  **半睁眼、无表情或极淡的疲惫**，背景是深紫蓝。
- 两张都用**带底不透明图**（满卡出血，两条边由卡的边缘吃掉）→ **完全绕开键控风险**。
- 两张共同的第一构图指令：**主体偏右上，左下留大面积安静区给文字**（否则文字没地方放）。
- **代码合成**：两张都预加载（避免切换闪白）；`[data-theme='light'] .oshi-art--night { opacity: 0 }`。
  - ⚠ **动效纪律（教训 21）**：给图做淡入**不要用 `transition: opacity` 和卡片自己的 `transition: transform` 写在同一元素上**
    （两条 `transition` 会互相覆盖）。做法：`transition: opacity` 只写在图自己的类上、卡片 hover 位移留在 `.oshi-card`（现状就是分开的），
    或者干脆用一次性的 `@keyframes` 淡入。
  - 可选加法：切换瞬间加 120ms 的"雪雾"遮罩（一层模糊白），**把这个切换变成一次眨眼**——
    成本几乎为零，但让"两个人"这件事被看见。`prefers-reduced-motion` 下直接切换。

### 6.4 文字与资料如何参与构图

| 内容 | 去哪 |
|---|---|
| 8 项资料 | **压在图上**（不再是旁边一列），保持网格（可扫读），靠一条**长渐变 scrim**（不是整块压暗）保证 ≥4.5:1。<br>**位置在两套主题下完全相同**——这就是"尺不动"的表达 |
| 姓名 | 字号提到 2rem+，压在图上，两套主题位置完全一致 |
| 主题句 + 签名句 | 图的安静区（左下）；亮色深字、暗色浅字，**字号不变** |
| 单元名 | 等宽小签，压在图上边缘 |
| **不擅长 表达情绪** | 暗色下**升级为全卡最大的一行**（见 6.2） |
| 版权小字 | **必须从图上挪走**——留在图下方一条窄带上（背景干净）。压在图上会逼你把 scrim 加重，那就把画毁了 |

- **可访问性**：DOM 完全不变（8 项 + 3 句），顺序不变。
  两张图里**只有一张进 DOM 的 `<img alt>`**，另一张用 `aria-hidden="true"` 的装饰层（`background-image` 更好，
  装饰层不该有 alt 语义）。
- ⚠ **不要用 `<picture>` + `prefers-color-scheme` 做切换**：站点的主题是 JS 手动切、写在 `data-theme` 上的，
  可能与系统偏好相反。**必须走 `[data-theme]` 选择器 + 两个图元素。**
- 分时：不需要 hover——**主题切换本身就是交互**。

### 6.5 亮 / 暗双主题
**"亮暗都要成立"在这里就是设计的核心命题**，逐条验收：
两套下文字对比 ≥4.5；**两张图的脸落在同一像素位置**；切换无位移、无闪白、无跳动。

### 6.6 390 / 320
- 手机端必须压短（现状 1025 / 1415）：
  - 图作为**卡顶满宽出血图**（`aspect-ratio: 3/2`，取脸与肩），高度 ≤ 现状顶图槽的 260–300px → **不更长**；
  - 资料区改"标签 + 值"紧凑行（省 300px+）；主题句与签名句并成一块；
  - 预计 **390 ≈ 900px（比现状短约 120）**、**320 ≈ 1150px（比现状 1415 短）**。
- **手机上这个方向的体验反而更强**：屏幕小，她的脸占比大，一按开关整张卡"变天"。
- **唯一需要分别调参的地方**：竖图裁成横图时两张的脸位置会不同 → 用**同一个 `--oshi-face-y` 变量**分别锁住
  `object-position`，保证两张的裁切一致。

### 6.7 性能
- **2 张带底图**（各 1200×1600 源 → WebP 目标 ≤90KB），**合计 ≤180KB**。
  **这是四个方向里最重的**（但两张都在懒加载、非首屏）。
- 可以优化：Astro 的 `widths`/`sizes` 只生成实际需要的档位；不要为了省体积在手机上只加载一张（那会毁掉这个方向）。
- **诚实说明**：这个方案的体积代价是可感知的；若在意，用 §6.9 的降级版（1 张图）。

### 6.8 实现代价与风险
- **最难一步：造出两张"同机位"的图。** 对策：**用图生图**——
  先出暗色那张（构图定稿），再以它为基底、用编辑词生成亮色那张：
  「保持构图、人物位置与大小、裁切、脸在画面中的位置与五官特征、发束走向、服装、姿势与透视完全不变，
  只改光照（改成左上方的柔和日间自然光）、时间与氛围、背景（深紫蓝夜 → 极简明亮的冷白室内）、
  表情（半睁的疲惫 → 礼貌克制的极浅微笑，眼型脸型不变）、整体提亮、饱和度略降保持冷调」。
  这正是上一轮"**文生图修不动的病灶，图生图编辑一次全中**"经验的正用——而编辑最擅长的恰好就是"只改光照"。
- **第二风险：两张的脸不一致**（编辑很容易微调脸）。
  对策：编辑词首尾双锁"脸部特征、眼睛形状与颜色、发束位置不得改变"；
  **验收时把两张叠在同一坐标做像素 diff 目视**（Playwright 截图叠加即可）。
- **第三风险：文字压在亮色图上的可读性**。对策：亮色那张的**构图**必须预留左侧 45% 的低对比区
  （写进提示词的**正向**要求，不靠 scrim 硬压），scrim 只做兜底。
- **a11y**：无结构风险；但"双主题下字号与位置严格一致"必须验——**两张截图做像素 diff 是最直接的判据**。
- **替代还是新增**：**替代**。

### 6.9 降级版
**只出 1 张图**（暗色的"里"，既是她的本色、也是站点的夜主题就绪状态），
亮色下用 `filter: brightness(1.12) saturate(.55)` + 一层浅色 veil 伪装成"表"。
观感肯定不如两张，但**"一按开关她变了"这件事仍然成立**，图的数量减半、体积减半。
**这是全提案里最划算的一个降级。**

## 7. 被否掉 / 搁置的想法（简短，供复核）

1. **全屏大图 + 文字压上（"把卡做成小 Hero"）** —— 站内 Hero 已经是这个语汇（`/` 的官方卡面 + 居中大字）。
   重复使用等于**把这张卡降级成"第二个 Hero"**，而它本该是全站唯一"属于她的东西"。
2. **八项资料各配一枚小图标的卡片扇（横向 fanned cards）** —— 8 张图的一致性成本高、
   且八枚图标会与站内 emoji 圆章（三游戏的法术）抢语汇；读起来更像"图鉴"，不是"单推"。
3. **CRT 扫描线 + 乱码（"她在屏幕里"）** —— 是 Nightcord 的另一种表达，但会压低文字可读性，
   且与站点"柔和、几乎察觉不到"的动效基调（`--ease-soft` / `--dur-*`）正面冲突。
4. **给整张卡加 `background-image` 装饰** —— 会吃掉玻璃卡的 `backdrop-filter` 透明感与首屏预算
   （上一轮 proposal §6 第八条已列此禁令）。本提案四个方向都**不新增全屏图**。

## 8. 如果只能做一个 → 选 A，三步走

**选 A「水槽」，理由是四个方向里唯一同时满足下面五条的：**

1. **它直击诊断**：诊断说"图只改了一个列宽数字"，A 是唯一一个**改变版式法则**（信息按水面分层）的方向——
   它让画面的物理决定了文字的排序。B 改的是发言主体（更"有趣"，但风险也更大），C 是排版语言，D 是状态。
2. **一份资产解决两个主题**（水色由令牌推导），且**不需要两张图**（对比 D）。
3. **DOM 顺序 = 视觉顺序 = 读屏顺序，a11y 零风险**（对比 B 的结构重排、C 的绝对定位 pull quote）。
4. **顺带修掉手机端最长的部分**：390 从 1025 → ~900，320 从 1415 → ~1050–1150，**四个方向里唯一"手机端明确变短"的**。
5. **可以分两步交付**：第一步纯 CSS（零素材）就能验证核心命题，第二步才出图。**每一步都能停在一个可交付的状态。**

**A 的最小可行版本（MVP，按顺序做）：**

| 步 | 做什么 | 成本 | 交付判据 |
|---|---|---|---|
| 1 | **纯 CSS 版的"水"**：删 `.oshi-moon` 与 `.oshi-snow`；加一层水面渐变 + 一条高光线；把 8 项拆成"线上 6 项网格 / 线下一项（不擅长 表达情绪，字号 +1 档 + 一个 CSS 气泡点）"；主题句移入水下 + 加一份 `scaleY(-1)` + `blur(3px)` + `opacity:.35` 的倒影（`aria-hidden`）；版权行沉到卡底；补 `prefers-reduced-motion` | 约 120 行 CSS + 模板小改 | 1440/390/320 × 亮/暗 六张图；**320 卡高 ≤ 1200**；读屏顺序与视觉顺序一致 |
| 2 | **出 1 张图**（3:4、700×1100、纯绿键控底、硬边发束），去背成透明 WebP ≤55KB，按 §A.3 两层 `clip-path` 接入 | 3–5 轮生成 + 1 个 Pillow 去背脚本 + 接入约 1h | 1440/390/320 × 亮/暗；她在两种主题下都穿水面线；水线不穿脸；构建后 `dist/_astro/` 里那张图 ≤55KB |
| 3 | **暗色的"入水"变体**：`[data-theme='dark']` 把水面线移到卡外（整卡在水下）+ 一条 CSS 光柱 | 约 30 行 CSS | 暗色下"最显眼的东西"是她与光柱，不是一颗球；`/`、`/projects/` 等页面不受任何影响 |

**次选**：如果用户更想"这张卡一眼就让人记住"，而不是"版式上有主张" → **D**（开关即人格，
概念最锋利、最容易被截图传播），代价是 2 张图与同机位的生成纪律。
**若用户想要"最保险、最像设计工作室做的"** → **C**。

## 10. 共用纪律与验收（四个方向都要过）

**落地纪律（写代码时别踩已记过的坑）**
1. 新类名先 grep：`src/styles/global.css`、`packages/design-kit/base.css`、所有 `<style is:global>`
   （`IntroOverlay` 的 `.intro`、`MusicDock`、`profile.astro` 各有一块）。**建议继续用 `oshi-` 前缀——已确认全局唯一。**
2. 令牌真源在 `packages/design-kit`，**不要在 `global.css` 里重写品牌色阶/表面色/圆角/阴影**。
   本提案新增的颜色（水色 / 水面高光 / 光柱）都应做成 `.oshi-card` 上的**局部变量**，由令牌推导。
3. **给图片加淡入用 `animation`，不要用 `transition: opacity`**（教训 21：会和卡片图已有的 `transform` 过渡互相覆盖）。
4. **`prefers-reduced-motion`**：删掉或改造 `.oshi-snow` 时必须补兜底（现状这张卡缺，属既有缺陷）。
5. 图片一律 `src/assets/` + `astro:assets` 的 `Image`（内容哈希 → `/_astro/*` immutable 长缓存）；
   **不要 `public/` 裸文件**（7 天陈旧区）。`loading="lazy"` + 显式宽高。
6. 装饰性图片 `aria-hidden="true"`；有信息含义的图必须有 `alt`；
   **"用图代替文字"的场合，文字语义必须留在 `aria-label`/`title` 或 DOM 文本里**（教训 16 的文案规范：
   基础功能不加解释性文案）。

**每条的验收动作**
1. `npm run build` / `npm run check`（0 errors）/ `npm run lint` / `npm test` 四绿。
2. Playwright 截图 **1440 / 390 / 320 × 亮 / 暗（六张）**，覆盖 `/about/`；
   **滚动必须 `behavior:'instant'` 且等 `.reveal` 拿到 `is-visible`**，否则截到 `opacity:0`（教训 30）。
3. **硬判据**：
   - 两套主题下所有文字对比度 ≥ 4.5:1（尤其新色：水色、scrim 之后的文字）；
   - **卡高不增加**：390 ≤ 现状 1025、320 ≤ 现状 1415（A/B 应明显更低）；
   - **读屏顺序 = 视觉顺序 = DOM 顺序**（键盘 tab 一遍确认）；
   - 搜索仍能命中资料（`162cm`、`田辺留依`）；
   - **320 无横向滚动**。
4. 构建后去 `dist/_astro/` 核对实际交付体积（源码体积 ≠ 交付体积：上一轮三个封面源 1.0–1.7MB、构建后 50–110KB）。
   体积红线：A ≤55KB（退成两张则 ≤110KB）、B ≤70KB、C ≤70KB、D ≤180KB（降级版 ≤90KB）。

## 11. 一句话收口

这版平庸的根源不是排得不好，而是**这张卡的设计动作只有一个：给文字减宽**——
图只改了一个列宽数字，八项等权，"不擅长表达情绪"和"162cm"一样重，装饰是等着被替换的占位符，
主题开关只换来换色。四个方向各自换掉了这条因果链里的一环：
**A 让画面的物理决定信息的顺序（事实浮着、心事下沉）**、B 让画面成为一段对话里的附件、C 让她的轮廓决定文字的形状、
D 让主题开关变成一次人格切换。**推荐 A：它与诊断一一对应，一份资产同时解决亮暗，a11y 零风险，
手机端明确变短，而且第一步不出图就能交付。**
