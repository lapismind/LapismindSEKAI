> 提出者：主美（艺术总监）视角

> 依据：仓库规范与踩坑记录 + 上一轮封面生图经验 + 逐张看过的现有素材 + 实际渲染页面的截图与几何实测。

## 0. 边界声明（先说清楚，免得这份提案被当成施工单）

- 根 `AGENTS.md` 的「不改已交付、不改已上线」我理解为**不擅自重做已上线的视觉**，而不是「任何页面都不能碰」。因此下面每条都标了 **替代 / 新增**：
  - **新增**类（往空处放东西，不移动任何现有元素）：风险最低，可以直接排期。
  - **替代**类（换掉一张已在线上生效的图）：改动的是用户已经验收过的画面，**必须先由用户拍板**再动手。
- `blog/AGENTS.md` 写死的禁区我一条都没碰，也没提：看板娘的 `#l2d-widget` 位置与尺寸、`.l2d-card`、`place()` 定位算法、`--corner-*` 变量。**本提案中没有任何一条建议移动、缩放或给她加背景。**
- 每条的量化和风险都写了依据，不做「可以考虑增加一些氛围插画」这种不能落地的话。

### A2 · 全站 OGP 分享卡（P0）

1. **位置**：`blog/src/components/BaseHead.astro`——第 6 行 `import FallbackImage from '../assets/soup-lobby.png'`，第 20 行 `image = FallbackImage`，第 218 行 `og:image`。已 grep 确认：**11 个页面/布局没有一处传 `image=`**。
2. **元素类型**：分享卡（OGP / Twitter Card）。
3. **解决什么问题**：这是一个**功能性缺陷**，不是观感问题。现在把 `/about/`、`/blog/`、`/works/`、任何文章分享到微信/Discord/X，预览图都是**海龟汤的大厅截图**——内容对不上，且截图里 26 张官方头像铺满，是版权暴露面最大的一张图。修好它，等于让站点的每一次外链都带上正确的第一印象。
4. **生成路线**：
   - **AI 只出底图（1–3 张）**，接线是代码活。
   - 需要的底图：
     - **全站通用 1 张**：文生图。夜雪 + 一条 SEKAI 的路/一扇门这种「世界观缩略图」，**中轴留空**给文字。
     - **`/about/` 1 张**：可与 A1 复用同一张真冬半身图（换构图裁切）。
     - **`/projects/` 1 张**：**不需要生图**——把三张已有封面横向拼贴成 1200×630 即可（脚本 10 分钟）。
   - **文章页不需要生图**：`BlogPost.astro` 已经在用文章自己的 `heroImage`，只要把它传给 `BaseHead`（代码 2 行）。
   - **文字怎么来**：**不要让模型渲染文字**（上一轮已确认卡面「只画图标、不写文字」才稳）。做法是「AI 出无字底图 → 用代码/Pillow 叠站名与 eyebrow」。若不想叠字，纯图 + `L` 品牌标也成立——很多站点就这么做。
5. **尺寸 / 比例 / 格式**：
   - **1200×630（1.905:1）jpg 或 png，≤300KB**。*不要给 OGP 用 WebP*：部分抓取器不认。
   - 走 `astro:assets` 的 `Image` 时显式 `format="jpg"`，并传 `widths={[1200]}`；或做成固定文件放 `public/og/`（代价：落进 7 天缓存区，换图有陈旧期，见 site-features §8）。**推荐前者**，因为 `og:image` 的 URL 写在同一个 HTML 里、会跟构建一起变。
   - 手机上分享卡多用 1.91:1 横向裁切，所以**主体别贴上下边**，居中偏上留 5% 安全区。
6. **难度与风险**：**低**。静态图、不进首屏解码路径、不进客户端渲染。唯一坑是「叠字」这一步的字体——用站内已有的霞鹜文楷屏显（`public/fonts/`）或 Atkinson，别用系统字体。
7. **替代还是新增**：**替代** `FallbackImage`；页面级为新增。
8. **工作量与优先级**：底图 1 轮生成 + 1 轮修（约 1 小时）；接线 2–3 小时（改 `BaseHead` + 8 个调用点传参）。**P0：立刻可做，收益明确。**
9. **验收**：`npm run build` 后 `grep -o 'og:image[^>]*' dist/**/*.html` 逐页核对指向不同文件；用 X/Discord 的卡片调试器或 `curl -A "<浏览器 UA>"` 确认线上 200 且 `content-type` 是图片；1440/390 不需要看图（图不进页面渲染），但要确认 HTML 体积没被 base64 之类的方式撑大。

### A1 · `/about/` 单推角色卡的真冬半身插画（P1 ★ 只做一条就选它）

1. **位置**：`blog/src/pages/about.astro` 的 `oshi · 单推` 区块（第 431–462 行），容器是 `.oshi-card`（CSS 第 217–229 行）。
2. **元素类型**：角色半身插画（新增到卡片右侧空区，向右出血）。
3. **解决什么问题**：
   - 这是全站唯一一张「角色卡」——8 项资料 + 主题句「在夜与雪之间，寻找真正的自己。」+ 签名台词「谢谢你，找到了我。」——**却没有任何角色形象**。整站是「真冬主题的个人站」，但她本人在 `/about/` 这张专门为她做的卡上缺席。
   - 卡片的空区不是我的猜测，是**代码自证的**：`.oshi-moon`（220×220 径向渐变光斑，锚 `top:-70 right:-60`）与 `.oshi-snow`（6 个 CSS 圆点当落雪）都是**抽象占位**，而且 moon 特意锚到卡外 + 靠 `overflow:hidden` 裁切——这张卡从写出来那天就是按「要放一个出血的装饰元素」设计的，只是那个元素一直没画。
   - 实测空区：`.oshi-facts` 只占 612/700 行宽（右侧余 118px），其下方到 `y≈1484` 是空的；右上那 220×220 光斑之外没有任何东西。可用的作画窗口约为**卡片右上方 230×365**，出血后可见部分约 230×365（图可以画 600×900，大部分被卡边裁掉，这正是 `overflow:hidden` 的用法）。
4. **生成路线**：**文生图**（不能走编辑——现有能当基底的只有官方卡面，做图生图会把官方构图与版权一起继承）。用 **`.planning/2026-09-17-游戏封面/refs/mafuyu-casual.jpg`（真冬常服参考）作为角色锚**，这是上一轮攒下的、裁掉水印的干净参考，别浪费。
   - 提示词必须写死的三件事：
     - 比例与脸：「少女比例，脸不要长，眼型不要成人化」——上一轮的实锤病灶就是「脸长、眼型成人化」。
     - 参考图纪律：常服参考是**双臂平举的 T 字模型照**，必须明写「不要照抄这个姿势、不要照抄这张没有表情的脸」。
     - 构图：**半身（腰以上）、右侧出血、看向左下方（朝向卡片里的文字）、背对/侧身**，把「单推」写成「她在看着这张卡的资料」而不是「她在给你做海报」。
   - 风格锚：**沿用 `.planning/2026-09-17-游戏封面/prompt-v3-围坐收敛版.md` 的收敛写法**（平涂、硬边阴影、少色阶、干净线稿、**单点发光**、背景大面积留空），这样她与三张游戏封面、页脚馒头人共处一页时不打架。
5. **尺寸 / 比例 / 格式**：
   - 画 **900×1200（3:4 竖）**，输出**带透明通道的 WebP**（或在夜雪底上做成"无缝融入"的不透明图，二选一；见风险 3）。
   - 接入时可见区约 230×365，所以 900×1200 里真正入画的只有左侧 2/5 ——**构图时就要把人放在画布左半边，右半边可以干脆画成空的**，否则裁切后会只剩一只胳膊。
   - 目标体积：**≤60KB**（它不在首屏，且 `/about/` 页面本身很轻）。走 `astro:assets` 的 `Image`（自动哈希 → `/_astro/*` immutable 长缓存）。
6. **难度与风险**：
   - **角色一致性（中）**：真冬的识别点＝深紫高马尾＋米色发圈＋半睁的"营业表情"、蓝紫瞳。参考图能锚住，但「像不像」得试 3–5 轮。**这是本项最花时间的地方**。
   - **手（中）**：裁在腰以上并且明写「手不入画或只露出一只手臂」——上一轮 v4.1 的五个补丁没落地里就有一条是腿部解剖。**能靠构图回避就不靠模型画。**
   - **AI 味（中）**：单张角色图最容易发光堆叠。收敛写法同封面。
   - **接入风险（低但要注意）**：图片会改变卡片内部的换行/高度。**必须确认卡片高度变化极小**（目标：≤±20px），否则 `/about/` 下方「这个站的世界」会整体下移——`/about/` 是已上线页面，这是它的可见代价。
7. **替代还是新增**：**新增**（不动 `.oshi-moon`、不动 `.oshi-snow`、不动任何文字与网格；只在卡片里加一层定位好的图）。这是本提案里最"干净"的一条。
8. **工作量与优先级**：生成 3–5 轮（1–2 小时）；接入约 1 小时（一个容器 + `Image` + 两条媒体查询）。**P1。**
9. **验收**：
   - 四图复核：1440 / 390 × 亮 / 暗，共 4 张。
   - 硬判据：① 图片右缘被卡片裁切、看不出是"贴上去的方图"；② 亮色下不发灰、暗色下不发亮（见第 5 节双主题检查）；③ `.oshi-card` 高度变化 ≤20px；④ 390 下若保留图片，不得压到"生日/年龄…"这几行文字的对比度（推荐 390 下**隐藏**，只留桌面版——这张卡的信息在手机上已经排满 1038px 高）。
   - `npm run build` / `check`（0 errors）/ `lint` / `test` 四绿。

### A3 · 首页 Hero 的原创雪夜插画（P1 · 价值最大、风险最高，需你拍板）

1. **位置**：`blog/src/pages/index.astro` 的 `.hero` / `.hero-photo`（第 49–78 行），当前图 `mafuyu-hero.webp`。
2. **元素类型**：全屏场景插画（Hero）。
3. **解决什么问题**（三个缺口，都有实测依据）：
   - **版权**：Hero 是全站最大的一张图，用的是官方卡面「交相辉映的笑容」，而且原图右下角还带着官方 logo 残留。页脚虽然写了版权与 "非官方粉丝向" 声明，但这是**直接搬运官方素材最重的一处**。原创重绘能把这一处从源头去掉。另外 `blog/docs/site-features.md` 第 6 节的"待办候选"里，**第一项就是「首页原创雪夜 Hero 插画」**——站点自己早就记下了这件事。
   - **观感**：浅色主题下，`.hero-photo::after` 的 5 段渐变叠上 `background-color: color-mix(in oklab, var(--primary-soft) 55%, var(--page-bg))`，把这张官方卡**洗到几乎不可辨**（截图实测：只剩一片灰白雾，人物轮廓要靠想象力）。文字对比度实际是靠 `text-shadow: 0 2px 8px rgba(0,0,0,.75)` 硬撑的。一张**为 Hero 专门构图**的图（深色雪夜、主体偏右、左侧本来就是暗部）能一次解决"洗白了"和"文字压不住图"两个问题，而且能卸掉那 55% 的 `color-mix` 遮罩。
   - **移动端取景**：实测 —— 桌面取景是**整张图**（y≈41–953），手机 390×675 只取到**图内 x≈642–1276，也就是中间 33% 宽的竖条**，而 `.hero-inner` 在手机上宽 350/390，**文字几乎盖满整个视口**。官方卡是中轴构图的，所以手机上主角被切在两边缘，中间留给你的只有一片空教室。横构图 + 中心构图这两件事天然打架。
4. **生成路线**：**文生图**（官方卡面不能当基底，否则版权和构图一起继承；`background-position: center 22%` 取的是横向取景，要重新设计）。
   - **本项最重要的一条美术指令**（可直接写进提示词）：**中轴 1/3 必须是安静的低对比区（夜空 + 落雪），主体放在右 1/3**。因为：
     - 桌面取整张，右 1/3 有主角就够了；
     - 手机只取中间 33%，那里正好是"安静区"，文字放上去不会打架。
   - 主题锚：夜、雪、SEKAI 的冷调，与海龟汤封面的夜雪是同一套色彩语言（那是最成功的一张），也与 IntroOverlay 的夜雪母题呼应。
   - 角色是否入画：**建议先出「无角色的纯场景版」验证风格**，再决定要不要加人。加人的话她进入手机取景区以外（右 1/3），风险最低。
5. **尺寸 / 比例 / 格式**：
   - **2400×1300（1.85:1）**。理由：桌面盒子是 2.11:1，用 1.85:1 的图 `cover` 后是裁上下、不裁左右（主体在右 1/3 不会被裁掉）；再宽就会在手机上把中间 33% 压得更窄——**不要做 21:9，那会让手机裁切窗口更接近纯中间，主体更容易丢**。
   - **目标 ≤130KB WebP**——现有 `mafuyu-hero.webp` 是 130KB，**新图不得更重**（站点 2026-09-15 刚做过一轮无损瘦身，见 site-features §8）。
   - 走 `astro:assets`（现在的实现是 `background-image: url(...)` 用了 `HeroBg.src`，继续沿用即可）。
6. **难度与风险**：
   - **AI 味（高）**：这是全站最大的一张图，AI 味的放大倍数最高。上一轮的六个来源（发光密度、元素塞满、线稿偏软、成人化脸、星芒/速度线、满屏特效）在这里都会更显眼。**必须按收敛写法**（第 5 节），并接受"可能要多轮"。
   - **移动端取景（高）**：换图后**必须重跑我的裁切算术**（不是看桌面觉得好看就行）。这条是本项唯一"能不能做成"的判据。
   - **夜景体积（中）**：深色渐变 + 雪粒很容易把 WebP 压不下去。如果 >130KB，宁可减少雪粒密度也不要为了体积把它压出块状。
7. **替代还是新增**：**替代** `mafuyu-hero.webp`。但**不要删原图**——留作 fallback，也留作"用户更喜欢官方卡面"时回退。
8. **工作量与优先级**：生成 4–8 轮（最容易 AI 味，约半天）；接入 30 分钟（换 import；如果移动端取景调不过来，可能要在 `.hero-photo` 加一条 `@media` 改 `background-position`——**一条媒体查询，不要动 `.hero` 的其他参数**）。**P1：内容价值与风险都是最高的，建议排在 A2 之后、由你拍板再动。**
9. **验收**：
   - 四图复核（1440/390 × 亮/暗），**手机那张是重点**：中间 33% 里没有主体、没有文字压不住的亮斑。
   - Hero 区域文字（h1 / lead / 按钮）在**亮色主题**下不靠 text-shadow 也能站得住（理想情况：可以削弱 `::after` 的最后一层 `color-mix` 遮罩）。
   - 体积：构建后 `dist/_astro/mafuyu-hero.*.webp` ≤130KB。
   - 首屏观感：`.hero-photo` 有 `hero-fade 0.9s` 与 `AnimationDelay 0.15s`，新图不能超过这个节奏能掩盖的范围（别把大图变成"先白后亮"）。

### A4 · IntroOverlay 三块斜切卡面的原创重绘（P1 · 图生图编辑路线）

2. **元素类型**：全屏插画 ×3（斜切三块拼贴）。
3. **解决什么问题**：
   - **版权**：三张官方「特训前/后」卡面全屏播 2 秒，是"直接搬运官方素材"面积第二大的地方（仅次于 Hero）。三张加起来 1600×719 ×3，是全屏尺寸。

5. **尺寸 / 比例 / 格式**：保持 **1600×719**，逐张 ≤ 现有体积（50 / 135 / 78 KB）——新图不得更重。Astro 侧不变。
6. **难度与风险**：
   - **脸心锚点回退（高，本项最大风险）**：三块斜切窗口（`.intro-p1/p2/p3` 的 `clip-path`）是按"脸高占屏 52%、脸心锚到 16.2%/39.9%、47.4%/41.8%、79.2%/38.8%"调出来的，而这些数字来自**用户红圈标注 → 红色像素质心**（lessons 第 7 条，纯几何、零误差）。重绘后如果人脸在画面里动了，斜切窗就会切到脸——**必须重新复核脸心**（沿用同一套红圈质心法），不要用视觉模型读脸部坐标（lessons 第 7 条记了四套模型各说各话）。
   - **动画节奏（低）**：`intro-ken` 有 `scale(1.06)→1.02` 的推镜，边缘不能有会被推镜暴露的接缝。
   - **"用户喜不喜欢"（中）**：这三张卡是用户挑的，动机可能是"我就喜欢这三张特训卡"。所以这条必须当成选择题给他们：**（a）只统一色温；（b）完全原创重绘；（c）不动。**
7. **替代还是新增**：**替代**，但保留原文件以便回退。
8. **工作量与优先级**：3 张 × 2–3 轮编辑（约半天）+ 脸心复核 1 小时。**P1**（版权收益明确，但风险与工作量都在，且需要用户先选路线）。

   - `prefers-reduced-motion` 下不播（现有逻辑），且体积不增加。

### A5 · 成就展馆的徽章图标集（P2）

   - **不要**做成大图或全屏背景——404 是低流量页，不值得任何首屏成本。
7. **替代还是新增**：**新增**。
8. **工作量与优先级**：2–3 轮生成 + 30 分钟接入。**P2。**
9. **验收**：亮/暗 × 1440/390 四图；图在两种主题下都不"贴片感"；`/404` 的 HTML 体积增加 < 1KB（除图片本身）；不影响 `.code`（渐变大字）的视觉重心。

## 5. 生成纪律（沿用上一轮攒下的经验，别丢）

### 5.1 文生图 vs 图生图编辑：怎么选
- **有现成基底、且"构图/位置不能动、只想改观感或统一风格"→ 图生图编辑。**（A4）
  - 编辑词要短（上一轮实测 **2067 字符**，上限 10000），**只写病灶**，首尾明确锁死范围。
  - 判据：文生图反复修不动的病灶（连续三版都改不掉的），换编辑一次全中——基底图即真源。
- **基底不能继承（版权 / 构图要重新设计 / 当前根本没有图）→ 文生图。**（A1 / A3 / A2 / A6）
- **图标集/徽章 → 文生图出一张图集再切**（A5），绝不逐张生成。

### 5.2 「AI 味」的六个来源与收敛写法（上一轮实测有效的部分）
出图提示词里固定写进这几条：`flat matte anime-cel shading`、`hard-edged shadows`、`few tone steps`、`clean line art`、`single light source`、`mostly empty background`；固定否掉：`no glow bloom`、`no sparkles`、`no star bursts`、`no speed lines`、`no floating particles`、`no lettering / numbers / logos / watermarks`。
- **发光密度**是最重的来源（上一轮满屏绿色辉光 + 速度线 + 星芒 + 漂浮牌）。**只留一处发光**。
- **留白是人画的，AI 会把每一格填满**。主动在提示词里要"大面积空白"。
- **线稿要硬**：往"更少色阶、更明确的明暗交界"走，别要柔和渲染。
- **脸**：明写「少女比例，脸不要长，眼型不要成人化」——上一轮四张脸全中这条病。
- **卡面只画图标不写文字**（上一轮结论），文字一律用代码/DOM 叠。
- **漫画强调符号（惊叹线、速度线）要明写允许**才可能出现（模型默认不敢加）——本提案里只有 A3 有可能用得上，其余全部禁止。

### 5.3 尺寸、格式、体积的硬规矩
- **出图直接出最终比例**，不要在站内用 CSS 裁。上一轮封面出的是 1024×1024 方图，接进 2:1/16:9 的列表位被迫二次裁切——那次的教训别重演。
- **走 `src/assets/` + `astro:assets` 的 `Image`**（自动内容哈希 → 落进 `/_astro/*` 的 `immutable, max-age=31556952`，见 site-features §8）。**不要**往 `public/` 里丢裸文件再用固定路径引用——那落进 7 天缓存区，换图有最长 7 天陈旧期。
- **唯一的例外是 OGP**：它必须有一个抓取器能拿到的绝对 URL，且 `.webp` 兼容性差 → 用 **jpg**，1200×630（A2）。
- 明确的体积红线（现有基线，别把它们打回去）：
  - Hero：**≤130KB WebP**（现有 `mafuyu-hero.webp` = 1920×1097 / 130KB）
  - IntroOverlay 三张：**≤50 / 135 / 78KB**（不得比现状重）
  - 单推半身：≤60KB；404 小图：≤60KB；徽章 5 枚合计 ≤25KB
- 构建后去 `dist/_astro/` 核对实际产物（Astro 会按 `widths`/`sizes` 生成多档，源码体积不代表交付体积——上一轮三个封面的源 PNG 是 1.0–1.7MB，构建后 50–110KB）。

### 5.4 双主题与移动端：每次都要过的检查
- **不要为亮/暗各出一张图**。站点已有的解法是"上一层 `color-mix(... var(--page-bg))` 遮罩"（`.hero-photo::after` 就是这套）；单色/线稿图则用 CSS `mask` + `currentColor` 自动换色（A6 推荐）。
- **移动端两个断点都要看：390 与 320**（`blog/AGENTS.md` 记录过 320 挤压问题）。390 与 320 的差异主要出现在导航与卡片网格，图片本身注意"别贴边裁到主体"。
- Hero 的裁切算术必须重算（见 A3 的实测数字）；**这是唯一一条"桌面好看但手机上翻车"的高危项**。

### 5.5 落地纪律（写代码时别踩已经记过的坑）
- **不要动** `Live2dMascot` 的 `left/bottom/width/height`、`.l2d-ground`、`.l2d-particles`、`.l2d-card`、`place()`，也不要动 `global.css` 的 `--corner-*`。本提案没有一条需要碰它们。
- **新建 CSS 类名先 grep 全局样式**：`src/styles/global.css`、`packages/design-kit/base.css`、所有 `<style is:global>`（尤其 `IntroOverlay.astro` 的全局 `.intro`，它打进了全站共享 CSS——lessons 第 29 条，布局塌过一次）。新类名带前缀（建议 `og-*`、`oshi-art*`、`nf-*`、`ach-badge*`）。
- 令牌真源在 `packages/design-kit`，**不要在 `global.css` 里重写品牌色阶/表面色/圆角/阴影**；本站自有令牌只有 `--cursor-*`、`--lift-hover`、`--corner-*`。
- 新增图片会给 `Image` 加淡入吗？**用 `animation`，不要用 `transition: opacity`**（卡片图已有 `transition: transform`，两条 `transition` 会互相覆盖——lessons 第 21 条）。
- 验证脚本：**滚动触发型页面的验证必须 `behavior: 'instant'`**，否则 `.reveal` 假不触发（lessons 第 30 条）；定位用 `data-testid` 或稳定选择器；不要用 `networkidle` 判成败；查线上资源**必须带浏览器 UA**（Cloudflare 403）。
- 图片元素给了 `alt`（装饰性则 `aria-hidden`）；徽章这类"用图代替文字"的，文字语义要留在 `aria-label`/`title` 上（lessons 第 16 条的文案规范：基础功能不加解释性文案）。

### 5.6 每条统一的验收动作
1. `npm run build` / `npm run check`（0 errors）/ `npm run lint` / `npm test` 四绿。
2. Playwright 截图：**1440 / 390（+320） × 亮 / 暗**，覆盖图所在的页面；Hero 与 IntroOverlay 必须额外在手机宽度看一遍。
3. `dist/_astro/` 里核对实际交付体积，与 5.3 的红线对比。
4. 线上落地后用带 UA 的请求探一次那张图（确认 200 + 正确的 `content-type`），并强刷确认。

## 6. 不建议加 AI 图的地方（克制清单）

**一、看板娘周围的一切。**
她的 `left/bottom/size`、`.l2d-ground`（阴影是 CSS 画的、要和她脚底对齐）、`.l2d-card`（徽章锚 `left:50%; bottom:12px`）都是反复微调定下的。**尤其不要给她加背景图**——她是 WebGL 实时渲染 + 独立的 CSS 地面，任何静态背景都会在两者之间插进一条"贴片"的缝；而且她在窄屏与右下角电台按钮视觉相邻，这是**已知且接受**的状态。这一条我不提任何变体。

**二、`lobby-kit` 的 26 张头像。**
它们**不是纯图标**，是 PJSK 官方角色 chibi 头像（150×150，彩色圆底 + 半身 + 常服细节）。换成 AI 生成有三个硬伤：① **识别功能会失效**——头像在联机游戏里的作用是"那个紫头发的"，AI 版认不出是哪个角色，玩家选择的乐趣就没了；② 26 张的一致性正是 AI 最弱的环节，混在大厅网格里必然出现"几张特别出戏"；③ 它与同一界面里的官方 stamp 表情、官方曲绘同屏，风格一旦不齐会显得"脏"。
——**注意这条的另一面**：这 26 张**本身**是版权素材。但"用 AI 重画头像"不是解法（会牺牲识别度），要降低版权面应该去别的地方（比如 A2 的 OGP，那张截图里就铺满了这 26 张）。

**三、`chat-kit` 的 stamp 表情包。** 同理，且它们**带日文字**——AI 生图的文字渲染是老大难，重画必崩。

**四、音乐播放器的曲绘（`public/music/jackets/*`）。** 官方曲绘是这个功能的**内容本身**（"这首歌长什么样"），不是装饰。换掉之后播放器就从"电台"变成"一个用 AI 配图的播放器"。

**五、Header 的品牌标（`L` 方块）。** 30×30px 的方形渐变底 + 单字母，在 30px 上的可读性是所有方案里最好的；换成插画会糊成一团墨。favicon 已经是真冬 chibi 头（`favicon.svg` 内嵌 PNG），品牌的身份表达已经有了。要动就动 favicon 的边缘适配，不是重画。

**六、三个游戏的所有界面（重点回答"大堂/等待室/结算有没有空的地方"）。**
实测结论：**没有值得用插画去填的地方。**
- **大堂**：`max-w-md` 的窄列，标题 emoji + 昵称/头像编辑器 + 创建/加入 + 邀请提示。它的"空"是**刻意的呼吸感**（窄列居中），不是缺内容。
- **等待室**：`max-w-lg` 里依次是玩家列表、房主配置、主持报名、谜题选择、开局按钮。**只有 1 人时确实短**，但它是一个**等待态**——往里放插画，会把"等 3 秒"变成"等 1 张图"，而且每个新玩家入房都会重排。
- **对局/结算**：信息密度已经很高（牌桌是 SVG 六边形毯 + SVG 渐变筹码，8 法术是 emoji，结算有排名/按钮组）。再塞插画会挤掉信息。
- 还有两个具体理由：**体积与首屏**（这三站刚做完 UI 缺陷修复与 design-kit 令牌迁移，别引入新的视觉变量）；**风格**（三游戏是"浅色卡片 + emoji"的功能界面，与博客的玻璃卡/霓虹紫是两套语言，硬塞插画两套都受伤）。
- **唯一可接受的形式（如果你自己觉得等待室太干）**：**一个共享的空状态小图**放进 `lobby-kit`，三个游戏复用同一张、≤15KB、只放"玩家还没到齐"这一种状态。**不要**做三张、不要做每个界面一张——那才是"哪里能塞图就塞图"。

**七、博客文章的 hero 图（现在全是开发过程截图）。**
`design-kit-tokens.png`（令牌总览表）、MMD 时间线截图、牌桌实拍、编辑器截图——这些是**证据**，不是配图。博客的定位是"开发记录与踩坑笔记"，截图为证；换成 AI 插画会把证据降级成氛围图，**降低可信度**。
——**例外**：将来如果真的写"游戏世界观/剧情/角色"类文章，那才值得配原创插画（而且那时可以和 A1 共用角色锚）。

**八、任何新增的全屏图、`background-image` 装饰。**
站点刚做完无损瘦身（看板娘首屏 3465KB → 1756KB），玻璃卡的观感建立在 `backdrop-filter: blur` 上——给卡片加 `background-image` 会同时吃掉 blur 的透明感与首屏预算。**全站全屏图的总数应该停在 Hero + IntroOverlay 三块 + 页脚横幅**（本提案的 A3/A4 是替换、不增加数量），404 与单推卡的两张是小图，不在此列。

## 7. 顺手发现（非生图，但会影响"站看起来做完了没有"）

按价值排序，都实测过：

1. **首页「精选游戏」有两处字母占位，而三张 AI 封面已经做好了。**
   `blog/src/pages/index.astro` 第 24–26 行的 `projectImages` **只映射了 `turtle-soup`**，而且指向的是 `soup-lobby.png`（旧大厅截图）。实测 `dist/index.html` 里有 **2 处 `card-media-fallback`**：出包魔法师显示「出」、梭哈显示「梭」，都是渐变底上一个字；海龟汤显示旧截图。而 `/projects/` 列表页三张封面都正常。
   **这是当前站点视觉上最便宜的一次提升——加两行 import + 映射，不需要生图。** 建议先把这个做掉，再谈生图。（首页那三张卡是 348×174 的 16:8，三张封面分别是 16:9 / 16:9 / 16:9 裁切后的比例，`object-fit: cover` 能接住，但要按 16:8 重新看一眼裁切位置——尤其是出包那张的龙头。）
2. **OGP 的 fallback 问题**＝ A2，见上。
3. **`public/cursors/` 里约 433KB 文件没有任何引用。**
   `global.css:16-17` 只用了 `mfy-normal.png`（1.9KB）与 `mfy-link.png`（1.4KB）。目录里另外还有：两个 `.cur`（合计 **338KB**）、`mfy-candidate.png`（45KB）、`preview-sheet.png`（24KB）与 **20 张 `preview-*.png`**（合计约 60KB）——`preview-sheet.png` 还是带中文标签的开发用预览图。它们全在 `public/` 里、会随 `dist/` 上线，且因为不带内容哈希，落进的是 7 天缓存区。
   顺带：`blog/docs/site-features.md` §2 写的「自定义鼠标：`arrow.png`（默认）+ `pointer.png`（手型）」已经和实现（`mfy-normal` / `mfy-link`）不一致，文档过期了。
   **可能是为将来留的候选集，所以删之前先问你。** 但 `preview-sheet.png` + 20 张 `preview-*.png` 明显是挑选过程的中间产物，删掉最安全。

## 8. 一句话收口

这份提案只提了 **6 条**（P0 一条、P1 三条、P2 两条），并且用一整节写了 **8 类不加图的地方**——因为站点现在的问题不是"图太少"，而是**三处该有图的地方（首页精选位、OGP、单推卡）没有图，而两处最重的官方素材（Hero、IntroOverlay）承担了本不该由它们承担的抽象任务**。先补缺口、再谈原创替换，是这个站现在最划算的顺序。
