# showhand 错误记忆

> 供本项目复用。跨项目通用教训同步到外部通用错误记忆库（Agent 配置目录下的 `docs/通用错误记忆库.md`，不在本仓库内）。

## 2026-08-14

### 1. 首次提交误提交 node_modules（2763 个文件）
- 现象：`git add -A` 后 node_modules 全被提交（2763 个文件），commit 刷屏警告。
- 根因：showhand 还没建 .gitignore（Task 1 脚手架步骤被跳过），`npm install` 装完依赖后直接 commit。
- 修复：写 .gitignore（node_modules/dist/.wrangler/.dev.vars），`git rm -r --cached node_modules` 移除，重新 commit。
- 教训：**任何新项目 npm install 之前先建 .gitignore**；commit 前 `git status` 检查有没有 node_modules 混入。

## 2026-09-14

### 2. 观众席会卡死下注轮转（高危）
- 现象：有人输光转观众后，接下来每一局的下注轮都推不动，只能等 30 秒 Alarm 把观众逐个"弃牌"，桌面陷入长时间僵死。
- 根因：`beginBettingRound` / `doBet` / `alarm` 把**全量 `state.players`** 传进 `core/betting.js`，而 `nextPlayer` 和 `bettingRoundDone` 只判断 `folded`/`allIn`、**不看 `role`**。观众仍在 `state.players` 里且 `folded=false`，于是：
  1. `nextPlayer` 会把回合交给观众；
  2. 观众的 `bet` 还带着上一局的残留值，`bettingRoundDone` 的 `caughtUp`（所有活跃玩家都跟到 currentBet）永远为 false，`actedIds` 也永远不含观众 → 下注轮无法正常结束。
- 修复：下注状态机只接收 `this.handParticipants(state)`（本局开局座位快照），不再接收全量玩家；`beginHand` 额外清掉所有人的牌局残留（含观众的 `bet`），但**不能在 `toSpectator` 里清** —— 中途转观众的玩家已投入的筹码仍要参与本局结算。
- 教训：**纯函数状态机的输入要显式收窄到"本次的有效参与者"**，不要图省事传全量列表。`betting.js` 的单元测试全绿也没用：它的测试只喂了干净的玩家对象，没人构造过"带残留字段的观众"。旁路角色（观众/离线/已出局）混在同一集合里时，一定要有集成测试专门覆盖。

### 3. 下注期间底池与座位投入是冻结的
- 现象：一整轮下注过程中，中央底池和每个座位的"下注 X"标签都不动，要等该轮结束才跳一次。
- 根因：`doBet` 只广播 `bet_result` 和 `turn_to`，从不重播 `room_state`；前端 `RCV_BET_RESULT` 又把 `data.pot` 丢掉了。
- 修复：`doBet` / `alarm` 在轮转未结束时补一次 `broadcastState(state)`（底池与各座位投入是扑克的核心信息，必须实时）。前端相应不再自己修补 `currentPlayerId`，以紧随其后的 `room_state` 为准。
- 教训：**广播了增量消息不等于状态同步了**。凡是"状态里已有、界面要显示"的数字，要么保证每次变更都重播状态，要么让增量消息带全它。这里 `bet_result` 其实已经带了 `pot`，但没人用 —— 数据发出来不等于有人消费。

### 4. 最终排名会丢掉中途输光退席的玩家
- 现象：整场结束的排名只包含最后一局的参与者，早就输光转观众的玩家凭空消失。
- 根因：结算用 `handParticipants`（本局参与者）当最终排名，而 `finalStandings` 又按 `role === 'player'` 过滤 —— 输光的人已经是观众，两条路都会漏掉他。
- 修复：开牌时给在座玩家打 `everPlayed` 标记，最终排名按它过滤；打满局数时改用 `finalStandings`。
- 教训：**"参与者"和"当前在座者"是两个不同集合**，涉及历史战绩时必须区分。

### 5. 联调脚本长期是坏的，导致上面的 bug 没人发现
- 现象：`scripts/ws-*-test.mjs` 五个脚本有四个跑失败，全挂在同一类陈旧断言上：断言开局一次发满 5 张（七张则 7 张），而发牌早已改成"边发边下注"（五张开局 2 张、七张开局 3 张）。`ws-seven-test` 的下注循环还用 `!lastOf(ws,'bet_result')` 作条件，只允许每人发一次注，改多轮下注后永远走不到摊牌。
- 根因：发牌设计变更后没有同步这些脚本，它们就不再被信任、也没人跑，于是 `ws-spectate-test` 名义上测"输光转观众"却从没真正让玩家破产（那一局的输家只丢掉 1 个筹码的底注）。
- 修复：全部改成事件驱动（按 `turn_to` 计数，每个回合只行动一次），断言对齐当前发牌节奏，并补上对底池实时更新的校验；新增 `ws-rematch-test.mjs` 覆盖整场结束→再来一局。
- 教训：**坏掉的验证脚本比没有更危险**——它给出"这块有人测过"的错觉。改玩法设计时，凡是断言了具体数值的测试和脚本都要一起过一遍；跑不起来的脚本要么立刻修，要么删掉，不要留在仓库里当摆设。

## 2026-09-14

### 6. 新一局的首帧广播带着旧状态（`currentPlayerId`/档位都是上一轮的值）
- 现象：闷牌轮端到端脚本两次误判 —— 读到 `stage === 'blind'` 的 room_state 时 `currentPlayerId` 还是 null、`currentBet` 还是上一轮的值；客户端之所以没出问题，是因为它靠紧随其后的 `turn_to` 打补丁。
- 根因：`beginHand` / `armNextStage` 在**算档位与选定行动者之前**就 `broadcastState` 了一次（为了把发出的牌和底池推给客户端），而 `beginBettingRound` 只补发 `turn_to`、不补 `room_state`。于是服务端存在一个"半成品状态帧"。
- 修复：`beginBettingRound` 在设好 `currentLevel`/`currentPlayerId` 后补一次 `broadcastState`；`beginHand` 也先把闷牌轮起注档位写好再广播。
- 教训：**广播出去的状态帧必须自洽**，不能指望客户端用后续消息拼出正确状态。这类"半成品帧"在浏览器里看不出来（消息到达顺序掩盖了它），却会让任何按状态判断的测试/新功能读到不一致的快照。凡是"改了状态就广播"的地方，顺序都要过一遍：先算完，再广播。

### 7. 设计令牌四处抄写，文档与实现早已分叉
- 现象：`--color-brand-*` 这一段在三款游戏（showhand / abracadawhat / turtle-soup）里一字不差地各存一份；`docs/LOBBY-KIT-COLORS.md` 规定页面底应为 `#F2EBF7` 香芋浅紫，而博客实际用的是 `oklch(0.972 0.014 249)` = `#EFF7FF` 极浅冷调白（`--hue-bg = 283 - 34` 从紫偏到了蓝）。
- 根因：同一份设计值有多处副本、且没有校验，谁都不知道哪一份是对的，也没有任何机制会因为分叉而报错。
- 修复：抽出 `@lapismind/design-kit` 作为唯一真源（品牌色阶 + 表面令牌 + 基础样式 + 字体接入），三款游戏与博客改为消费它；`tests/tokens.test.mjs` 校验 oklch 与 hex 两处定义色相一致。`docs/LOBBY-KIT-COLORS.md` 改为只讲"为什么"，不再重复色值。
- 教训：**同一份值抄在多处，必然会分叉，而且不会报错**。判断标准不是"这段代码复不复杂"，而是"它是不是本该系统里只有一份"。文档里的色值也是副本，同样会烂掉——文档应该指向真源，而不是复制真源。

## 未解决

- **跟注免费导致打法退化**：底注只在开局扣一次且各阶段不清零 `bet`，`beginBettingRound` 又把起始档位设为"现有最大投入"，于是每个新阶段所有人的差额都是 0 —— 付完底注后可以一路免费过牌到摊牌，只有主动加注才会再进钱。默认打法会退化成"人人跟到底比牌"。（闷牌轮的起注档位是底注的 2 倍，所以**第一轮**不受这个影响，有真实成本。）
- **没有位置轮转**：`beginBettingRound` 里 `firstId = canAct[0].id`，永远按加入顺序的第一个活跃座位开局，同一座位每局每轮都先行动，系统性占便宜/吃亏。
- **闷牌的半价会被"补回"**：闷牌轮结束后档位按实际最大投入重置，所以闷牌省下的一半会在下一轮跟注时补上 —— 闷牌买到的是"用一半价钱先看一张牌"，中途弃牌才真正省下。这是当前规则的刻意选择（避免亮牌后仍享受永久折扣），但如果实测发现玩家觉得"闷牌没用"，可以考虑让档位跨轮沿用（那时闷牌者会一直保留折扣，需要重新做平衡）。
- 以上都属玩法平衡，改动会影响既有手感，需先定设计方向再动。
