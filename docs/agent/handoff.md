## 唯一的前提

**对话上下文不跨机器**——它在各机本地的 `~/.local/share/opencode/` 里，不同步，也不该同步。

所以能接手的唯一条件是一条：**离开这台机器前，把状态写进仓库并 push。**

仓库是唯一的接力载具。AGENT 配置、技能、会话历史、`node_modules` 都不需要（也不该）跨机器同步——
它们只影响"用什么方法干活"，不影响"干到哪了"。反过来，没写进仓库的东西，对另一台机器就等于没发生。

## 接力棒：`docs/session-logs/CURRENT.md`

- 它**只做索引**：一行一个进行中的任务——状态 + 指向，不写叙述（2026-09-29 契约降级，旧版"收工覆盖写"作废）。
- 状态的"叙述"——当前进度、下一步、决策原因、踩过的坑、为什么放弃了另一条路——住在**各任务自己的文档**里：
  计划任务在 `.planning/YYYY-MM-DD-任务名/`，项目内推进在该项目的 `docs/`（如 `niigo-party/docs/进度.md`）。
  这些文件随任务开工创建、随任务收尾更新，**不随每次提交更新**。
- 从 git 查不到的通用教训进 `lessons-learned.md`；里程碑只在"大版本 / 上线"这类节点才写
  `docs/session-logs/YYYY-MM-DD-主题-handoff.md`（结构见 [`archiving.md`](./archiving.md)），普通推进靠提交信息就够。
- **维护 CURRENT.md 的时机只有三个**：任务开工加一行；暂停或完成改状态；任务收口删行。
  大部分提交完全不碰它。

## 日常流程

**开工**

```powershell
.\scripts\sync.ps1 pull
```

然后让 Agent 先读 `docs/session-logs/CURRENT.md`（索引），需要细节再顺着指向的任务文档读。

**收工（离开这台机器前）**

```powershell
# 1. 核对 CURRENT.md 索引行是否仍准确（通常不用动；任务开始/暂停/完成才改）
# 2. 一条命令完成：提交 + 推送
.\scripts\sync.ps1 ship -m "blog: 动效落地，下一步标题装饰线调长度"
```

## 为什么强调"收工是一个动作"

唯一真实的失败模式是**忘**：忘 push，或者留一堆未提交改动就换机器。
后者会让另一台 `pull` 时冲突，而且冲突发生在你最没心情处理的时候。

所以 `ship` 会把「提交 + 推送」合成一次操作，并且：

- 工作区有改动 → 全部提交后再 push（不会漏）；
- 工作区干净但有未推送提交 → 直接 push；
- 两者都没有 → 明确告诉你"没有需要同步的东西"，而不是假装成功。

## 两条纪律

1. **先 pull 再开工。** 单机为主时它是备份核对；只要曾在另一台机器动过仓库，pull 就是防冲突的唯一手段。
2. **离开前必 ship。** 宁可提交一条"半成品"并写清"下次从哪继续"，也不要留着未提交的改动——
   工作区里的东西会被下一次任何人 ship 全量卷走（2026-09-29 实际发生过一次），归属就乱了。

## 硬限制（别指望靠机制绕过）

- 对话上下文不跨机器：**没写下来的等于没发生**。
- 不同步：`~/.local/share/opencode/`（会话历史/快照/缓存）、`node_modules`、各项目 `.dev.vars`（密钥）。
- `~/.config/opencode`、`~/.agents`、`AGENT` 配置目录这类 Agent 配置若两台不一致，只是"你用的技能/提示词不同"，
  不影响接力——**但那里的记录（关于我.md、通用错误记忆库.md）不同步，其中的内容不会自动跨机器。**
  需要跨机器的结论，写进仓库里的 `lessons-learned.md` / `docs/`。
- **两台设备的仓库路径不同**（如 `D:\LapismindSEKAI` 与 `C:\Projects\Web\LapismindSEKAI`）：仓库内的脚本与文档
  **一律写相对路径**，不写盘符。脚本用 `$PSScriptRoot`（PowerShell）或 `__file__`（Python）定位自身；
  文档用仓库内相对路径（`blog/`）或"在仓库根目录执行"。详见 [`../MIGRATION-NOTES.md`](../MIGRATION-NOTES.md) 第二节。
